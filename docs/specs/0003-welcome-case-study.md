# Spec: หน้า case study ที่ `/welcome` + สภาพแวดล้อมเดโมสาธารณะ

## Problem Statement

คนที่มาพิจารณาผลงานเปิด `/welcome` แล้วได้อ่านคำอธิบายกับดูคลิป แต่ **ไม่ได้ลองอะไรเลย** — ตัวระบบจริงอยู่หลังการเข้าสู่ระบบด้วย Google ซึ่งเขาไม่มีทางเข้า และคลิปก็ทำหน้าที่เล่าแทนทุกอย่างจนหน้าอ่านเหมือนโฆษณามากกว่างานวิศวกรรม สิ่งที่คนตัดสินใจจ้างหรือร่วมงานต้องการคือสามอย่างที่หน้านี้ยังไม่มี: ได้ลองของจริงด้วยมือตัวเอง · เห็นหน้าจอจริงหลายมุมไม่ใช่แค่รอบเดียว · และเห็นว่าเจ้าของงานคิดอย่างไรกับข้อจำกัด ตลอดจนกระบวนการที่ใช้สร้างมันขึ้นมา

## Solution

รีดีไซน์ `/welcome` ทั้งหน้า (แทนที่ของเดิมที่พาธเดิม ไม่เพิ่ม route) ให้ยืนบนสี่แกน — **Live Demo · Screenshots · Engineering Decisions · AI-assisted workflow** — พร้อมกับ **สภาพแวดล้อมเดโมจริงที่แยกจาก production โดยสิ้นเชิง**: Worker คนละตัว ฐานข้อมูลคนละก้อน ปุ่มเดียวเข้าได้โดยไม่ต้องมีบัญชี Google ข้อมูลเป็นชุดสังเคราะห์ที่รีเซ็ตเป็นระยะ และไม่มี side effect ออกไปข้างนอกเลย (ไม่ส่ง LINE จริง ไม่ตรวจสลิปที่เสียเงิน)

หน้าตายังเป็นภาษาของตัวแอปเอง (ขาว/น้ำเงิน minimal ไม่มีอนิเมชันเกินจำเป็น) เพราะความสอดคล้องระหว่างหน้าอธิบายกับตัวงานคือสิ่งที่หน้านี้กำลังพิสูจน์

## User Stories

1. ในฐานะคนที่มาดูผลงาน ฉันต้องการเปิดหน้าแนะนำได้โดยไม่ต้องล็อกอินและไม่ต้องสร้างบัญชี เพื่อดูว่างานนี้ทำอะไรได้
2. ในฐานะคนที่มาดูผลงาน ฉันต้องการ **กดปุ่มเดียวแล้วได้เข้าไปลองตัวระบบจริง** โดยไม่ต้องมีบัญชี Google เพื่อประเมินงานด้วยมือตัวเองไม่ใช่ด้วยคำโฆษณา
3. ในฐานะคนที่มาดูผลงาน ฉันต้องการรู้ทันทีว่าสิ่งที่ฉันกำลังดูอยู่เป็นข้อมูลตัวอย่าง ไม่ใช่ข้อมูลลูกค้าจริงที่ถูกเปิดเผย
4. ในฐานะคนที่มาดูผลงาน ฉันต้องการเข้าใจจากหน้าเว็บว่าเดโมนี้มีอะไรถูกปิดไว้ เพราะอะไร เพื่อไม่ให้เข้าใจผิดว่าฟีเจอร์พัง
5. ในฐานะคนที่มาดูผลงาน ฉันต้องการเห็นหน้าจอจริงของงานหลายมุม (ภาพรวม · บิลที่ส่งถึงผู้เช่า · การชำระเงิน) เพื่อประเมินคุณภาพของงานออกแบบ ไม่ใช่แค่ฟีเจอร์
6. ในฐานะคนที่มาดูผลงาน ฉันต้องการเห็นว่าอะไรคือโจทย์ตั้งต้นของงานชิ้นนี้ เพื่อตัดสินว่าการตัดสินใจต่าง ๆ สมเหตุสมผลกับบริบทหรือไม่
7. ในฐานะคนที่มาดูผลงาน ฉันต้องการอ่านข้อตัดสินใจสำคัญในรูปแบบ **ปัญหา → ตัดสินใจ → ผลที่ตามมา (รวมข้อเสีย)** เพื่อประเมินว่าคนทำคิดเป็น ไม่ใช่แค่ทำได้
8. ในฐานะคนที่มาดูผลงาน ฉันต้องการเห็นข้อเสียที่ยอมรับไว้อย่างตรงไปตรงมา เพื่อเชื่อว่าส่วนอื่นของหน้าไม่ได้ถูกเลาให้สวย
9. ในฐานะคนที่มาดูผลงาน ฉันต้องการเห็นว่ากระบวนการสร้างงานเป็นอย่างไรตั้งแต่ต้นจนจบ (Plan → Build → Verify) เพื่อเข้าใจว่าจุดไหนใช้เครื่องมืออะไร
10. ในฐานะคนที่มาดูผลงาน ฉันต้องการเห็นว่าส่วนไหน AI ทำ ส่วนไหนคนตัดสิน เพื่อประเมินฝีมือคนที่อยู่เบื้องหลัง
11. ในฐานะคนที่มาดูผลงาน ฉันต้องการเห็นหลักฐานของกระบวนการนั้น (เอกสารจริงในโปรเจค) ไม่ใช่คำกล่าวลอย ๆ
12. ในฐานะคนที่มาดูผลงาน ฉันต้องการเห็นว่าเครื่องมือตรวจสอบจับข้อผิดพลาดได้จริงในงานนี้ เพื่อเชื่อว่าคุณภาพถูกตรวจอย่างเป็นระบบ
13. ในฐานะคนที่มาดูผลงาน ฉันต้องการเห็นรายการเทคโนโลยีที่งานนี้ใช้จริง เพื่อประเมินว่าตรงกับงานที่ฉันกำลังหาคนทำหรือไม่
14. ในฐานะคนที่มาดูผลงาน ฉันต้องการกระโดดไปยังหัวข้อที่สนใจได้จากเมนู เพื่อไม่ต้องกวาดตาทั้งหน้า
15. ในฐานะคนที่มาดูผลงานที่สนใจตัวคนทำ ฉันต้องการช่องทางติดต่อที่กดได้จริงท้ายหน้า เพื่อสานงานต่อโดยไม่ต้องค้นหา
16. ในฐานะคนที่มาดูผลงาน ฉันต้องการเห็นโปรไฟล์งานอื่นของคนทำ เพื่อประเมินภาพรวมของฝีมือ
17. ในฐานะคนที่มาดูผลงานจากมือถือ ฉันต้องการหน้าที่ย่ออ่านได้จบโดยไม่ต้องซูมออกและไม่ล้นแนวนอน
18. ในฐานะคนที่มาดูผลงานจากที่เน็ตช้า ฉันต้องการให้หน้าโหลดไวและไม่ดาวน์โหลดไฟล์หนักโดยไม่จำเป็น
19. ในฐานะคนที่ใช้คีย์บอร์ดหรือโปรแกรมอ่านหน้าจอ ฉันต้องการอ่านหน้าจบได้ตามลำดับหัวข้อที่เข้าใจได้
20. ในฐานะคนที่ตั้งค่าระบบให้ลดการเคลื่อนไหว ฉันต้องการให้หน้าไม่ขยับตามการเลื่อน
21. ในฐานะผู้ชมที่กำลังอยู่ในหน้าจอสาธิต ฉันต้องการให้มีเครื่องหมายชัดเจนว่าฉันอยู่ในโหมดตัวอย่าง เพื่อไม่เข้าใจว่าข้อมูลพวกนี้เป็นของจริง
22. ในฐานะผู้ชมที่กำลังอยู่ในหน้าจอสาธิต ฉันต้องการกดใช้ทุกอย่างได้จริงรวมถึงแก้ข้อมูล เพื่อให้เห็นว่าระบบทำงานอย่างไรจริง ๆ
23. ในฐานะผู้ชมที่กำลังอยู่ในหน้าจอสาธิต ฉันต้องการรู้ว่าข้อมูลอาจถูกรีเซ็ตเป็นระยะ เพื่อไม่ตกใจถ้าสิ่งที่ทำไว้หายไป
24. ในฐานะผู้ชมที่กำลังอยู่ในหน้าจอสาธิต ฉันต้องการให้ข้อมูลเริ่มต้นมีของให้ดูครบทุกหน้า (แดชบอร์ด · รายการบิล · สถานะการชำระ) เพื่อไม่ต้องสร้างห้องและผู้เช่าเองก่อนจึงจะเห็นอะไร
25. ในฐานะผู้ชมที่กำลังอยู่ในหน้าจอสาธิต ฉันต้องการให้เดือนปัจจุบันยังว่างอยู่ เพื่อได้ลองทำพิธีกรรมต้นเดือนด้วยมือตัวเอง
26. ในฐานะผู้ชมที่กำลังอยู่ในหน้าจอสาธิต ฉันต้องการให้การกดส่ง LINE หรือตรวจสลิปแจ้งชัดว่าถูกปิดในโหมดตัวอย่าง เพื่อไม่เข้าใจว่าแอปค้าง
27. ในฐานะผู้ชมที่กำลังอยู่ในหน้าจอสาธิต ฉันต้องการให้หน้าจอที่ทำอะไรไม่ได้จริงในโหมดตัวอย่างมีคำอธิบายประกอบ เพื่อไม่เสียเวลางงว่าทำไมใช้ไม่ได้
28. ในฐานะเจ้าของโปรเจค ฉันต้องการให้ผู้ชมเข้ามาลองได้โดยไม่ต้องสมัคร เพื่อไม่ต้องมีระบบบัญชีสำหรับคนนอก
29. ในฐานะเจ้าของโปรเจค ฉันต้องการให้ปุ่มเข้าสู่หน้าสาธิตใช้ได้เฉพาะในสภาพแวดล้อมสาธิต และบน production ตอบว่าไม่พบเส้นทาง เพื่อไม่ให้มีประตูหลังในระบบจริง
30. ในฐานะเจ้าของโปรเจค ฉันต้องการให้เดโมใช้ฐานข้อมูลคนละก้อนกับข้อมูลจริงของหอ เพื่อไม่ให้ผู้ชมแก้ข้อมูลจริงได้แม้จะกดผิด
31. ในฐานะเจ้าของโปรเจค ฉันต้องการให้เดโมไม่มีทางส่งข้อความ LINE จริงหรือเรียกบริการตรวจสลิปที่เสียเงิน เพื่อไม่ให้มีค่าใช้จ่ายหรือข้อความถึงคนจริงจากการเล่นของคนแปลกหน้า
32. ในฐานะเจ้าของโปรเจค ฉันต้องการให้ข้อมูลเดโมถูกรีเซ็ตเป็นระยะ เพื่อไม่ให้หน้าสาธิตเน่าและไม่ต้องเข้าไปดูแลเอง
33. ในฐานะเจ้าของโปรเจค ฉันต้องการให้การรีเซ็ตหลีกเลี่ยงการทับงานของคนที่กำลังใช้งานอยู่ให้ได้มากที่สุดเท่าที่สภาพแวดล้อมที่ใช้ฐานข้อมูลร่วมกันจะทำได้ (ไม่ใช่การรับประกัน) เพราะการเห็นข้อมูลของตัวเองหายกลางคันเป็นความประทับใจที่แย่ที่สุดในเดโม
34. ในฐานะเจ้าของโปรเจค ฉันต้องการให้ข้อมูลที่แสดงบนหน้าสาธารณะทั้งหมดเป็นชุดสังเคราะห์เท่านั้น เพื่อไม่ให้ข้อมูลผู้เช่าจริงรั่วผ่านสือหรือเดโม
35. ในฐานะเจ้าของโปรเจค ฉันต้องการให้สือทุกชิ้นถูกถ่ายใหม่จากสภาพแวดล้อมตัวอย่างชุดเดียวกับเดโม เพื่อให้สิ่งที่หน้าเว็บโชว์กับสิ่งที่ผู้ชมเจอเป็นอันเดียวกัน
36. ในฐานะเจ้าของโปรเจค ฉันต้องการให้หน้าไม่กล่าวอ้างสิ่งที่ไม่มีจริง (ราคา จำนวนผู้ใช้ รีวิว โลโก้ลูกค้า) เพื่อให้ทุกประโยคบนหน้าตรวจสอบได้
37. ในฐานะเจ้าของโปรเจค ฉันต้องการให้หน้านี้ไม่แตะแอปเดิมนอกจากสิ่งที่เดโมจำเป็นต้องมี เพื่อไม่ให้งานที่ตรวจรับแล้วถดถอย
38. ในฐานะเจ้าของโปรเจค ฉันต้องการให้ค่าที่เปลี่ยนตามการ deploy (ที่อยู่เดโม · อีเมล · โปรไฟล์ GitHub) อยู่ในที่เดียวที่แก้ได้ก่อน deploy เพื่อไม่ต้องไล่แก้หลายจุดในวันขึ้นงาน
39. ในฐานะคนที่มาอ่านสเปกนี้ในภายหลัง ฉันต้องการให้สเปกของหน้าเวอร์ชันแรกยังอยู่ครบ เพื่อเข้าใจว่าอะไรถูกเปลี่ยนและเพราะอะไร

## Implementation Decisions

### ที่อยู่และเอกสาร
- หน้าใหม่**แทนที่ของเดิมที่พาธ `/welcome`** ไม่เพิ่ม route ใหม่ และไม่แก้ `not_found_handling` หรือพฤติกรรม asset server
- ยัง**ไม่เพิ่มลิงก์เข้า `/welcome` จากในแอป** และหน้าแรก `/` ยังเป็นหน้าเข้าสู่ระบบเหมือนเดิม
- สเปกนี้เป็นเอกสารใหม่ (`0003`) · สเปก `0002` **ไม่ถูกแก้ย้อนหลัง** ทำหน้าที่เป็นบันทึกของรุ่นแรก
- คำศัพท์บนหน้าใช้คำกลางของโดเมนตาม `CONTEXT.md` (ห้องพัก · ผู้เช่า · บิล · ปิดบิล · สลิป · คิวรอตรวจ · เหมาะกับเจ้าของหอคนเดียว)

เรียงตามนี้เท่านั้น — (1) Hero (2) บริบท + ห้าขั้นตอนของรอบบิล (3) Live Demo (4) Screenshots (5) Engineering Decisions (6) AI-assisted workflow (7) ท้ายหน้า + Footer

- **คำเรียกปุ่ม:** ปุ่มหลักของหน้าคือ `ทดลองระบบ` · **ห้ามใช้คำว่า "เปิดระบบ" ที่ใดบนหน้าอีก** · ปุ่มรองคือ `ดูว่าเขียนยังไง`
- **Hero:** คำโปรยบน · หัวเรื่องสองบรรทัด · ย่อหน้านำ · ปุ่มสองปุ่ม · ภาพหน้าจอที่ 1
- **บริบท + ห้าขั้นตอน:** ย่อหน้าเดียวว่าหอเล็กเจ้าของคนเดียวจัดการทุกอย่างเอง ตามด้วยแถบห้าขั้นของรอบบิลแบบย่อ (ไม่มีภาพ) — ทำหน้าที่เป็นกระดูกเรื่องเดิมที่พิสูจน์แล้วว่าได้ผล
- **Live Demo:** ปุ่ม `ทดลองระบบ` · สิ่งที่ผู้ชมจะเจอเมื่อเข้าไป · **คำกำกับว่าเป็นข้อมูลตัวอย่าง** · **รายการสิ่งที่ปิดไว้ในโหมดตัวอย่าง** (ส่ง LINE จริง · ตรวจสลิปที่เสียเงิน · การเชื่อม LINE ด้วยรหัสเจ้าของ) · **บอกตรง ๆ ว่าเดโมเป็นสภาพแวดล้อมที่ใช้ร่วมกัน ข้อมูลอาจถูกผู้ชมคนอื่นแก้หรือถูกรีเซ็ตได้ตลอดเวลา ไม่ใช่พื้นที่ส่วนตัวของแต่ละคน**
- **Screenshots:** สามภาพพร้อมคำอธิบายสั้นหนึ่งถึงสองบรรทัดต่อภาพ — แดชบอร์ดรายเดือน · บิลใน LINE พร้อม QR · สถานะการชำระและคิวรอตรวจ — **ห้ามนำภาพที่ใช้ใน hero มาแสดงซ้ำในส่วนนี้**
- **Engineering Decisions:** สี่เรื่อง รูปแบบ **ปัญหา → ตัดสินใจ → ผลที่ตามมา/ข้อเสียที่ยอมรับ** ต่อเรื่อง:
  1. **ผู้เช่าไม่มีบัญชี** — ช่องทางเดียวคือ LINE → ผลที่ตามมา: ผู้เช่าไม่ต้องติดตั้งหรือสมัครอะไร แต่การยืนยันตัวตนอ่อนกว่าการมีบัญชี และไม่มีหน้าจอฝั่งผู้เช่าให้ตรวจสอบย้อนหลังด้วยตัวเอง
  2. **ราคาถูกตรึงไว้ในบิล** — บิลเก็บทุกค่า ณ วันสร้าง → ผลที่ตามมา: แก้ค่าตั้งต้นภายหลังไม่ย้อนไปเปลี่ยนบิลเก่า แต่ต้องเก็บสำเนารายการและยอดไว้ในทุกบิล
  3. **ปิดบิลเองเมื่อยอดตรงเป๊ะ** — ไม่ต้องนั่งตรวจสลิปทุกใบ → ผลที่ตามมา: ระบบเชื่อผลตรวจของผู้ให้บริการภายนอก ถ้าสลิปปลอมหลุดรอดการตรวจและยอดบังเอิญตรง ระบบจะปิดบิลผิด — ยอมรับความเสี่ยงนี้เพราะมีเจ้าของคนเดียวและมีคิวรอตรวจรองรับกรณีผิดปกติ
  4. **ไม่มีงานตั้งเวลา** — ทุกอย่างเกิดจากคำขอจริง → ผลที่ตามมา: ไม่มีอะไรให้ดูแลเบื้องหลัง แต่ก็ไม่มีอะไรทำงานแทนคนเมื่อไม่มีใครเปิดระบบ
- **AI-assisted workflow:** แสดงลำดับสามขั้นเท่านั้น **Plan → Build → Verify** พร้อมชื่อเครื่องมือจริงต่อขั้น — Plan (ChatGPT · Claude) · Build (Codex · Claude Code) · Verify (ชุดเทส + การตรวจด้วยตาเปล่า) — พร้อมหลักฐานที่มีอยู่จริงในโปรเจคไม่เกิน **1-2 ชิ้นเท่านั้น** (เลือกจาก: สเปกตัวอย่าง · ตั๋วงานตัวอย่าง) **ห้ามเปิดเผย prompt หรือ log ภายใน และห้ามกล่าวอ้างตัวเลขที่ตรวจสอบไม่ได้**
- **ท้ายหน้า:** ปุ่ม `ทดลองระบบ` · ลิงก์โปรไฟล์ GitHub · ช่องทางอีเมล · Footer ที่มีแบรนด์และคำกำกับว่าข้อมูลทั้งหมดเป็นข้อมูลตัวอย่าง
- **โทนภาษา:** ไทยล้วน สุภาพ กระชับ ไม่มีเครื่องหมายอัศเจรีย์ · จำนวนเงินเป็นตัวเลขตามด้วย " บาท" · ไม่มีราคา แพ็กเกจ จำนวนผู้ใช้ รีวิว คำรับรอง หรือโลโก้ลูกค้า

### สือและภาพ
- **วิดีโอไม่ใช่ข้อกำหนดของหน้านี้อีกต่อไป** และไฟล์วิดีโอเดิมถูกลบออกจาก working tree และ repo (ประวัติ git ยังเก็บไว้): `demo.mp4` · `demo.webm` · `poster.jpg` · รวมถึงภาพ hero เดิม `hero-bills.webp` ที่จะถูกแทนด้วยภาพใหม่
- **หน้าหน้านี้ใช้ภาพจริง 4 ไฟล์เท่านั้น**: (1) หน้าสร้างบิล/กรอกมิเตอร์ — ใช้ในส่วน hero (2) แดชบอร์ดรายเดือน (3) บิลใน LINE พร้อม QR (4) สถานะการชำระและคิวรอตรวจ — สามภาพหลังอยู่ในส่วน Screenshots
- ภาพทั้งหมด**ถ่ายใหม่ทั้งหมด**จากสภาพแวดล้อมตัวอย่างที่ seed จากชุดข้อมูลสังเคราะห์ชุดเดียวกับที่เดโมใช้ — ภาพต้องคมพอสำหรับการแสดงผลจริง ไม่ใช่เฟรมที่ดึงจากวิดีโอ
- ภาพทุกใบระบุความกว้าง/ความสูงจริงใน markup เพื่อไม่ให้หน้าเลื่อนตอนภาพโหลด และมีคำอธิบายภาพ (alt) ที่บอกว่าภาพนั้นคือหน้าจออะไร ไม่ใช่คำโฆษณา
- ภาพสำหรับการแชร์ลิงก์ (OG) ต้องถูกถ่ายใหม่หลังหน้าเสร็จ เพราะของเดิมถ่ายจาก hero ที่ถูกแทน — ขนาดและเพดานน้ำหนักตามที่กำหนดไว้ในสเปกก่อนหน้า
- สือทุกไฟล์เป็น asset สาธารณะในโฟลเดอร์สื่อของหน้าตามเดิม และต้องผ่านขั้นตอน build ของโปรเจคก่อนจึงจะถูกเสิร์ฟ (ไฟล์ที่คัดลอกลง output ตรง ๆ จะไม่ถูกเสิร์ฟ — ทดลองแล้ว)
- ห้ามสือใดมีชื่อผู้เช่า เลขห้อง หรือยอดเงินจริงของหอ — ทุกชิ้นต้องมาจากชุดสังเคราะห์เท่านั้น

### สภาพแวดล้อมเดโมสาธารณะ
- **แยก Worker คนละตัว** ชื่อ `wangchan-demo` พร้อม D1 ของตัวเอง และ **R2 bucket ของตัวเอง** (จำเป็น: การไม่มี binding ทำให้บางเส้นทางคืน 500 และ health คืน 503) · URL ที่คาดคือ `wangchan-demo.<บัญชี>.workers.dev`
- **Invariant ที่ห้ามละเมิด:** binding ทุกตัวของ `wangchan-demo` (D1 · R2 · ตัวแปรลับทุกตัว) ต้องชี้ไปยัง resource ของเดโมเองเท่านั้น ห้ามชี้ resource ของ production แม้แต่ตัวเดียว — ตรวจด้วยการเทียบค่า id จริงของแต่ละ binding กับของ production ก่อน deploy ทุกครั้ง ไม่ใช่เชื่อจากชื่อไฟล์ config เฉย ๆ
- **DEMO_MODE ต้อง hard-block side effect ภายนอกในโค้ดโดยตรง ไม่ใช่พึ่งคีย์ที่เว้นว่างเพียงอย่างเดียว:** ทุกจุดที่เรียกออกนอกระบบจริง (ส่ง LINE · เรียกตรวจสลิปกับ SlipOK) ต้องเช็คค่าตั้งต้น DEMO_MODE ก่อนทุกครั้ง แล้วคืนผลแบบปลอดภัยทันทีโดยไม่ยิง request ออกไปเลย ไม่ว่าคีย์จะถูกตั้งไว้จริงหรือไม่ — ป้องกันกรณีมีคนตั้งคีย์จริงบนเดโมโดยไม่ตั้งใจ (เช่น copy ค่าจาก production ผิดที่) เพราะการพึ่งคีย์ว่างเพียงอย่างเดียวไม่ใช่การ์ดที่เชื่อถือได้ · คีย์ LINE และ SlipOK ยังคงเว้นว่างในเดโมเป็นชั้นป้องกันที่สอง (ชั้นแรกคือโค้ด) · หน้า settings ยังขึ้นว่ายังไม่ตั้งค่าตามพฤติกรรมเดิม · ปุ่มส่งบิลทาง LINE ตอบข้อความข้อผิดพลาดที่อ่านรู้เรื่องจาก DEMO_MODE โดยตรง ซึ่งหน้า landing ต้องบอกล่วงหน้า
- **ทางเข้าด้วยคลิกเดียว:** เส้นทางใหม่บนเดโม worker ที่สร้างเซสชันของผู้ใช้ตัวอย่างโดยเรียกตัวสร้างเซสชันเดิมของระบบ แล้วตั้งคุกกี้ — วันนี้ทั้งระบบมีทางออกเซสชันทางเดียวที่เรียกจาก callback ของ Google จึงเป็นโค้ดใหม่ และต้องไม่แตะเส้นทางของ Google
- **ประตู DEMO_MODE:** เส้นทางนี้ทำงานเฉพาะเมื่อค่าตั้งต้นของสภาพแวดล้อมเป็นค่าที่กำหนดเท่านั้น ถ้าไม่ตรงให้ตอบว่าไม่พบเส้นทาง (404) — ใช้รูปแบบการตรวจค่าตรงตัวที่ระดับเส้นทางและ fail closed แบบเดียวกับที่โปรเจคนี้ใช้อยู่แล้วกับเส้นทางสำหรับตรวจสอบ ไม่ใช่ middleware ทั้งระบบ
- **การรีเซ็ต (ประเมินความเสี่ยง ไม่ใช่การรับประกัน):** ข้อมูลตัวอย่างถูกรีเซ็ตเมื่อมีการกดเข้าเดโม แต่ข้ามการรีเซ็ตถ้าตรวจพบว่ามีคำขอเข้าเดโมภายใน 5 นาทีที่ผ่านมา — เก็บเวลาเข้าเดโมล่าสุดจริงในฐานข้อมูลของเดโมเอง ปรับค่าทุกครั้งที่มีคำขอเข้าเดโม ไม่ใช่แค่ตอนกดปุ่มเข้าครั้งแรก เพื่อประเมินว่าไม่น่ามีใครกำลังใช้งานอยู่ · **นี่คือการประเมิน ไม่ใช่การติดตามผู้ใช้จริง** เพราะเดโมเป็นสภาพแวดล้อมที่ทุกคนใช้ฐานข้อมูลร่วมกัน ผู้ชมสองคนที่เข้าพร้อมกันเห็นและแก้ข้อมูลชุดเดียวกันเสมอ ไม่มีทางแยกข้อมูลต่อคนได้ในสถาปัตยกรรมนี้ — หน้าเว็บต้องบอกข้อจำกัดนี้ตรง ๆ ห้ามใช้คำว่ารับประกัน หรือบอกว่าข้อมูลจะไม่ถูกรบกวนเด็ดขาด · ชุดคำสั่งรีเซ็ตต้องฝังมากับ Worker เพราะการรันคำสั่งฐานข้อมูลจากภายนอกตอนผู้ชมกดปุ่มทำไม่ได้
- **ชุดข้อมูลตั้งต้นของเดโม:** ห้องและผู้เช่าชุดสังเคราะห์ + **ประวัติบิลสองเดือนที่ครอบหลายสถานะ** (จ่ายแล้ว · ยังไม่จ่าย · มีสลิปรอตรวจ) + **ปล่อยเดือนปัจจุบันว่าง** เพื่อให้ผู้ชมได้ทำพิธีกรรมต้นเดือนด้วยมือตัวเอง
- **แก้ข้อมูลได้จริง** ในเดโม ไม่ทำโหมดอ่านอย่างเดียว — ปุ่มที่กดแล้วไม่เกิดอะไรคือสิ่งที่ทำให้เดโมดูพัง
- **ไม่มี side effect ออกนอก:** ห้ามเดโมส่งข้อความ LINE จริง · ห้ามเรียกบริการตรวจสลิปที่เสียเงิน · ห้ามแตะ R2 ของ production
- **ตัวชี้โหมดตัวอย่างในตัวแอป:** เปลือกของแอปต้องแสดงเครื่องหมายถาวรว่าเป็นข้อมูลตัวอย่าง/โหมดสาธิต โดยฝั่ง Worker เป็นผู้บอกสถานะนี้แก่ฝั่งหน้าเว็บ — **วันนี้ยังไม่มีของเดิมในซอร์ส จึงเป็นงานใหม่**
- ค่าที่เปลี่ยนตามการ deploy (ที่อยู่เดโม · อีเมลติดต่อ · โปรไฟล์ GitHub) อยู่ในที่เดียวที่แก้ได้ และปล่อยเป็นค่าตั้งต้นว่างไว้ก่อน — **ห้ามใส่ค่าปลอมลงหน้าเว็บ**

### ข้อกำหนดทางเทคนิคอื่น
- ไม่เพิ่ม dependency ใหม่ และไม่เปลี่ยนวิธีเสิร์ฟหน้า (ยังเป็น HTML เดียวที่เรนเดอร์จากฝั่ง Worker โดยไม่มีเฟรมเวิร์กฝั่งไคลเอนต์)
- กลไกการเลื่อนเปิดหัวข้อคงของเดิมแบบจังหวะเดียว ไม่เพิ่มอนิเมชันใหม่ และต้องยังอ่านครบเมื่อปิด JavaScript
- โทเคนสี/ระยะ/รูปทรงทั้งหมดยังคัดจากธีมของแอป ห้ามคิดค่าใหม่
- การแก้ฝั่งแอปจำกัดอยู่ที่สิ่งที่เดโมต้องใช้เท่านั้น: ประตู DEMO_MODE · ทางออกเซสชันสำหรับเดโม · ตัวชี้โหมดตัวอย่างในเปลือกแอป · การตั้งค่าของ worker ตัวที่สอง — **ไม่แตะหน้าจอหรือพฤติกรรมเดิมของแอป**

## Testing Decisions

- **หลักการ:** เทสเฉพาะพฤติกรรมภายนอกที่ผู้ใช้หรือระบบภายนอกรับรู้ ไม่ผูกกับรายละเอียดภายใน และไม่ยืนยันข้อความบนหน้าแบบยกหน้าทั้งก้อน
- **Seam เดิม seam เดียว:** ขอบเขต HTTP ของ Worker ผ่านชุดเทสที่มีอยู่ — หน้าใหม่และเส้นทางของเดโมเข้ามาอยู่ใน seam นี้ได้โดยไม่ต้องมี harness ใหม่
- **เทสของหน้าเว็บ (ปรับจากชุดเดิม):** เปิดได้โดยไม่ต้องมีเซสชันและไม่พึ่งฐานข้อมูล · เป็นหน้าของเราจริงไม่ใช่ markup ของ SPA · สมอในหน้าทุกตัวต้องมีปลายทางจริง · **ห้ามมีคำว่า "เปิดระบบ" ที่ใดในข้อความที่ผู้ใช้เห็น** · ปุ่มหลักชี้ไปที่ที่อยู่เดโมที่ตั้งไว้ · มีคำกำกับข้อมูลตัวอย่างและรายการสิ่งที่ปิดในโหมดตัวอย่าง · **หน้าไม่มีองค์ประกอบวิดีโออีกต่อไป** · ภาพทั้งสี่ถูกอ้างถึงพร้อมขนาดจริง · ลำดับส่วนถูกต้องตามที่กำหนด · โทนคำไม่มีเครื่องหมายอัศเจรีย์ · คู่สีที่ใช้จริงผ่านระดับ AA · ปุ่มสูงอย่างน้อย 44px · ยกเลิกการเคลื่อนไหวใต้ reduced-motion
- **เทสของเดโม (สำคัญที่สุดของสเปกนี้):**
  - **ประตูต้อง fail closed** — เมื่อค่าตั้งต้นของสภาพแวดล้อมไม่ใช่ค่าโหมดสาธิต เส้นทางทางเข้าต้องตอบว่าไม่พบเส้นทาง และต้องไม่สร้างเซสชันหรือแก้ข้อมูลใด ๆ
  - **ทางเข้าสร้างเซสชันให้ผู้ใช้ตัวอย่างได้จริง** เมื่อเปิดโหมดสาธิต และตั้งคุกกี้ที่ใช้เข้าแอปได้
  - **การรีเซ็ตคืนข้อมูลชุดตั้งต้นได้จริง** — หลังทำให้ข้อมูลเพี้ยนไปแล้ว การเข้าเดโมต้องคืนค่ากลับเป็นชุดตั้งต้นตามที่กำหนด (จำนวนห้อง ผู้เช่า บิล และสถานะที่คาดไว้)
  - **การเช็กกิจกรรมล่าสุดทำงานตามที่ออกแบบ** — ถ้ามีคำขอเข้าเดโมภายใน 5 นาทีที่ผ่านมา การเข้าเดโมครั้งใหม่ต้องข้ามการรีเซ็ต และเทสต้องพิสูจน์ว่าเป็นการเช็กกิจกรรมจริง ไม่ใช่แค่เวลานับจากการรีเซ็ตครั้งก่อน
  - **ไม่มี side effect ออกนอกแม้จำลองว่ามีคีย์จริงตั้งอยู่** — เมื่อ DEMO_MODE เปิดอยู่ การเรียกส่ง LINE หรือตรวจสลิปต้องไม่ยิง fetch ออกไปจริง แม้ mock ค่าคีย์ LINE/SlipOK ให้เป็นค่าที่ตั้งไว้จริงก็ตาม เพื่อพิสูจน์ว่า DEMO_MODE กันไว้ก่อนถึงคีย์เสมอ ไม่ใช่พึ่งคีย์ว่าง
- **สิ่งที่พูลเทสยืนยันไม่ได้ ต้องตรวจด้วยมือตอนปิดงาน:** พฤติกรรมจริงของ deployment เดโม (health ตอบปกติพร้อม bucket ของตัวเอง · ปุ่มส่งบิลให้ข้อความที่อ่านรู้เรื่องโดยไม่ยิงออกจริง) · ที่อยู่เดโมจริงกดแล้วเข้าได้ · เนื้อหาในภาพทั้งสี่เป็นชุดสังเคราะห์และคมพอในการแสดงผลจริง · ตัวชี้โหมดตัวอย่างปรากฏในเปลือกแอปของเดโม · หน้าเดิม `/` ไม่เปลี่ยน · ไม่มีข้อมูลจริงในสือหรือในเดโม · **binding ทุกตัวของเดโม (D1 · R2 · ตัวแปรลับ) ชี้ resource คนละก้อนกับ production จริง เทียบ id ทีละตัว**
- **Prior art:** ชุดเทสของหน้าเดิม (`test/welcome.test.ts`) และตัวช่วยอ่านสไตล์ร่วมในชุดเทส · รูปแบบการทดสอบเส้นทางที่ fail closed ตามค่าตั้งต้นมีอยู่ในโปรเจคแล้ว (เส้นทางสำหรับตรวจสอบ)
- **ด่านสุดท้าย:** `npm run check` ผ่านทั้งเส้น ไม่มีไฟล์ชั่วคราวตกค้าง และ pre-deploy blocker ทั้งสามข้อใน Further Notes ต้องปิดครบก่อนสั่ง deploy `wangchan-demo` จริง

## Out of Scope

- การขาย การตลาด ราคา แพ็กเกจ การทดลองใช้ จำนวนผู้ใช้ รีวิว คำรับรอง โลโก้ลูกค้า
- การรองรับหลายหอหรือหลายผู้ใช้ (multi-tenant) การสมัครใช้งานสำหรับเจ้าของหอรายใหม่ และการรับผู้ใช้จากภายนอกเข้าสู่ระบบจริง
- ส่วน "ไม่เหมาะกับใคร" และการเปรียบเทียบกับคู่แข่ง
- วิดีโอและสือเคลื่อนไหวทุกชนิดบนหน้า
- เส้นทางใหม่สำหรับหน้า (หน้าแทนที่ที่เดิม) และการเพิ่มลิงก์จากในแอป
- การเปลี่ยนภาษาภาพ ฟอนต์ หรือระบบดีไซน์ของแอป
- อนิเมชันเพิ่มเติมหรือลูกเล่นการเลื่อนแบบใหม่
- การเปิด repo ของโปรเจคเป็นสาธารณะ (เลื่อนออกไปจนกว่าจะตรวจประวัติและสิทธิ์การใช้งานเรียบร้อย)
- ระบบสมัคร/ยืนยันตัวตนแบบอื่นสำหรับเดโม (เช่น รหัสผ่านชั่วคราว หรือ Access) — ใช้ทางเข้าคลิกเดียวแบบมีประตูเท่านั้น
- งานตั้งเวลาสำหรับรีเซ็ตเดโม — การรีเซ็ตผูกกับจังหวะที่ผู้ชมเข้าใช้

## Further Notes

- **ข้อจำกัดที่ห้ามละเมิด (เข้มที่สุด):** ห้ามข้อมูลผู้เช่าจริงปรากฏบนหน้าเว็บ ในสือทุกชิ้น หรือในเดโม — ทั้งหน้าอธิบายและเดโมใช้ชุดข้อมูลสังเคราะห์เท่านั้น และตัวชี้โหมดตัวอย่างต้องทำให้ผู้ชมไม่มีทางเข้าใจผิด

### 🔴 Pre-deploy blockers — ปิดครบทุกข้อก่อน deploy `wangchan-demo` หรือขึ้นหน้าใหม่บน production

1. **ชีตข้อมูลของหอเปิดให้อ่านได้โดยไม่ต้องมีสิทธิ์** — ที่อยู่ของชีตถูกฝังอยู่ในสคริปต์ที่ track อยู่ และการเรียกอ่านแบบสาธารณะคืนข้อมูลได้จริง (ตรวจแล้วด้วย curl ตรง ๆ) ต้องเปลี่ยนสิทธิ์ของชีตเป็นส่วนตัว และย้ายที่อยู่นั้นออกจากไฟล์ที่ track — เรื่องนี้เร่งด่วนที่สุดและไม่เกี่ยวกับ `/welcome` เลย ควรปิดก่อนงานอื่นทั้งหมดในสเปกนี้
2. **คำตอบจริงจากบริการตรวจสลิปที่ฝังอยู่ในไฟล์เทส** (เลขอ้างอิงจริง วันที่ ยอด และบัญชีผู้รับ) ต้องถูกแทนด้วยข้อมูลสังเคราะห์
3. **ตัวอย่างและชุดทดสอบที่ใช้เลขห้องจริงของหอและชื่อจริงของผู้เช่า** (`bills.tsx` · `rooms.tsx` · ไฟล์เทสที่เกี่ยวข้อง) ต้องถูกแทนด้วยของสังเคราะห์ — `bills.tsx`/`rooms.tsx` เป็นโค้ดฝั่งไคลเอนต์ที่ deploy ไปกับ `wangchan-demo` ด้วย placeholder จริงจะไปโผล่ในหน้าจอที่ผู้ชมเดโมเห็นตรง ๆ ไม่ใช่แค่ปัญหาตอนเปิด repo

- **งานก่อนเปิด repo สาธารณะ (ไม่บล็อกการ deploy demo):**
  4. ไฟล์สิทธิ์การใช้งาน (LICENSE) ยังไม่มี และการไล่หาข้อมูลจริงทั้งประวัติ git ต้องทำให้จบก่อนเปิด repo — โปรเจคนี้ยังไม่มี remote จึงยังไม่มีอะไรถูกเผยแพร่
- **งานตอน deploy จริง (ไม่ใช่ blocker แต่ต้องทำตอนนั้น):**
  5. ค่าจริงของที่อยู่เดโม อีเมลติดต่อ และโปรไฟล์ GitHub ต้องถูกเติมก่อน deploy (หน้าปล่อยเป็นค่าว่างไว้ก่อน)
- **ความเสี่ยงที่ยอมรับ:** ผู้ชมเดโมแก้ข้อมูลได้จริงและใช้ฐานข้อมูลร่วมกับผู้ชมคนอื่นเสมอ การเช็กกิจกรรมล่าสุดก่อนรีเซ็ตช่วยลดโอกาสที่ข้อมูลจะถูกรีเซ็ตทับระหว่างมีคนใช้งานอยู่ แต่ไม่ใช่การรับประกัน — ผู้ชมสองคนที่เข้าพร้อมกันยังเห็นและแก้ข้อมูลชุดเดียวกันเสมอ · เดโมมีต้นทุนการรันเท่าโปรเจค Workers ทั่วไป และไม่มีงานตั้งเวลาให้ดูแล
- **ADRs ที่เกี่ยวข้อง:** การเลือก Cloudflare Workers เป็นแพลตฟอร์มเดียว และการปิดบิลอัตโนมัติเมื่อยอดตรง — ข้อตัดสินใจที่ 3 และ 4 ของหน้าเป็นการเล่าเรื่องจาก ADR เหล่านี้ ไม่ใช่การเปลี่ยนข้อสรุป
