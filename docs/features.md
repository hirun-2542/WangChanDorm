# พฤติกรรมของระบบ (รายละเอียด)

เอกสารนี้เก็บรายละเอียดระดับ implementation ของ Wang Chan Dorm — API แต่ละตัวรับส่งอะไร,
เงื่อนไขการปิดบิล, นโยบายการคิดเงิน, LINE bot, การยืนยันตัวตน และโครงสร้างไฟล์

README ที่รากโปรเจกต์เป็นภาพรวมสำหรับคนที่เพิ่งเปิด repo ครั้งแรก ถ้าต้องแก้โค้ดในส่วนไหน
ให้อ่านหัวข้อที่ตรงกันในไฟล์นี้


## ห้องพักและค่าใช้จ่ายประจำ

- ตาราง `room_charges(id, room_id, name, amount, position)` เก็บค่าใช้จ่ายประจำของแต่ละห้อง (ค่าเริ่มต้น เช่น ค่าบริการ 10, ค่าขยะ 20, ค่าไวไฟ 100) มี index บน `room_id`; ห้องหนึ่งมีได้ไม่เกิน 10 รายการ
- `GET /api/rooms` — ทุกห้องมี `charges: [{ name, amount }]` เรียงตาม `position` (array ว่างเมื่อยังไม่มี) โดยคงฟิลด์เดิมและลำดับห้องเดิมไว้ครบ
- `PATCH /api/rooms/:id` — รับ `charges` แบบไม่บังคับ; เมื่อส่งมาจะแทนที่รายการเดิมทั้งชุด (ลบแล้วเพิ่มใน `DB.batch` เดียว) ไม่ส่งมาจะไม่แตะรายการเดิม; ตรวจว่ารับ array ไม่เกิน 10 รายการ แต่ละรายการมีชื่อ (ตัดช่องว่างแล้วต้องไม่ว่าง) และจำนวนเงินเป็นจำนวนเต็ม ≥ 0 ไม่งั้น `400` พร้อม field `charges`
- ค่าเริ่มต้นเหล่านี้ถูก snapshot ลง `bill_charges` ของบิลที่สร้างแล้ว แก้ค่าเริ่มต้นของห้องภายหลังจึงไม่กระทบบิลเก่า
- หน้า แก้ไขห้อง มีตัวแก้ไข "ค่าใช้จ่ายประจำ" (ชื่อ + จำนวนเงิน, เพิ่ม/ลบได้) บันทึกไปพร้อมห้อง

## บิลรายเดือน

- `period` เป็น ค.ศ. รูปแบบ `YYYY-MM` (เช่น `2026-09` = กันยายน 2569) เก็บในตาราง `bills` ฝั่ง client เป็นหน้าที่แปลงเป็น พ.ศ.
- `GET /api/bills?period=YYYY-MM` — บิลของเดือนนั้น เรียงตามเลขห้อง พร้อมชื่อห้อง/ผู้เช่า วันที่ออก bิล (`createdAt`) และค่าใช้จ่ายเพิ่มเติม (camelCase, แบน)
- `GET /api/bills/meter-sheet?period=YYYY-MM` — เฉพาะห้องที่มีผู้เช่าปัจจุบัน เรียงตามเลขห้อง พร้อม `waterPrevious`/`electricPrevious` จากบิลล่าสุดของห้อง (หรือเลขเริ่มต้นตอนสร้างห้อง), อัตราที่ใช้จริง (override ของห้อง ?? ค่า default จาก settings), `existingBillId` เมื่อห้องนั้นมีบิลของเดือนนี้แล้ว และ `charges` (ค่าใช้จ่ายประจำของห้องนั้น) ให้หน้า สร้างบิล เติมไว้ล่วงหน้า
- `POST /api/bills/generate {period, entries:[{roomId, waterCurrent, electricCurrent, flatElectricAmount?, charges?}]}` — เซิร์ฟเวอร์คิดยอดเงินเองทั้งหมด (หน่วย × อัตรา ปัดขึ้นเสมอด้วย `chargeFromUnits` (ดู "นโยบายการคิดเงินรายเดือน"), ห้องเหมาใช้ยอดที่ส่งมา, total = ค่าห้อง + น้ำ + ไฟ + ผลรวมค่าใช้จ่ายเพิ่ม) แล้วเขียนบิลและค่าใช้จ่ายเพิ่มใน `DB.batch` เดียว; ตรวจทั้งหมดก่อนเขียน (ถ้าไม่ผ่านจะไม่เขียนอะไรเลย) — มิเตอร์ย้อนหลัง `400`, ห้องว่าง/ไม่พบห้อง `400`, สร้างซ้ำเดือนเดิม `409`
- `PATCH /api/bills/:id {waterCurrent?, electricCurrent?, flatElectricAmount?, charges?}` — แก้บิลที่ยังไม่จ่าย (`paid` ตอบ `409`); คำนวณหน่วย/ยอดใหม่จากอัตรา snapshot ของบิลเดิม; ส่ง `charges` เป็น array เต็มเพื่อแทนที่รายการเดิม (array ว่าง = ลบทั้งหมด); ห้องเหมาต้องส่ง `flatElectricAmount` (หน่วย/อัตราไฟคงเป็น null) และห้องมิเตอร์ห้ามส่ง; มิเตอร์ต่ำกว่า `waterPrevious`/`electricPrevious` ของบิล `400`; เขียนบิลและค่าใช้จ่ายใน `DB.batch` เดียว
- `DELETE /api/bills/:id` — ลบบิลที่ยังไม่จ่ายพร้อมค่าใช้จ่ายทั้งหมดใน batch เดียว (`paid` ตอบ `409`, ไม่พบ `404`); **บิลที่มีสลิปอ้างถึงลบไม่ได้** (`409` "บิลนี้มีสลิปอ้างถึงอยู่ ลบไม่ได้ — ตรวจสลิปในคิวรอตรวจให้จบก่อน") เพราะ `slips` มี FK มาที่ `bills` เพื่อให้ย้อนตรวจได้ว่าสลิปเทียบกับใบไหน — เดิมกรณีนี้ตอบ `500 INTERNAL` ผ่าน `isForeignKeyViolation()` แล้วตอบ `409` พร้อมทางออกแทน
- `POST /api/bills/:id/mark-paid {method: transfer|cash, paidAt?}` — ปิดบิลเอง ตั้ง `status = paid` พร้อม `paid_at`/`paid_method`; `paidAt` เป็น ISO `YYYY-MM-DD` หรือ timestamp เต็ม (ไม่ส่งใช้เวลาปัจจุบัน); ช่องทางผิด `400`, ปิดซ้ำ `409`, ไม่พบ `404`
- บิลเก็บ snapshot อัตรา เลขมิเตอร์ โหมดค่าไฟ และค่าใช้จ่ายเพิ่ม ณ วันสร้าง แก้ settings หรือโหมดของห้องภายหลังไม่กระทบบิลเก่า

### ส่งบิลทาง LINE

- `POST /api/bills/:id/send` — push บิลใบนั้นเป็น Flex message ให้ผู้เช่าที่เชื่อม LINE แล้ว; ไม่พบบิล `404`, ผู้เช่ายังไม่เชื่อม `409` (ไม่ส่งอะไร), LINE ปฏิเสธ/เชื่อมไม่ได้ `502` และ**ไม่**บันทึก `sent_at`; สำเร็จ `{ok:true, bill}` พร้อม `sentAt` ใหม่
- `POST /api/bills/send-all {period}` — push ให้ทุกบิลของเดือนนั้นที่ผู้เช่าเชื่อมแล้ว ตั้ง `sent_at` เฉพาะใบที่ส่งสำเร็จ นับใบที่ล้มเหลวไว้โดยไม่หยุดทั้งชุด แล้ว push สรุปให้เจ้าของ (จำนวนบิล, ยอดรวม, ส่งสำเร็จกี่ใบ, ใครยังไม่เชื่อม); เดือนที่ไม่มีบิล `400`; คืน `{ok, period, sent, failed, skipped:[{roomNumber, tenantName}]}` — เจ้าของยังไม่เชื่อม LINE ก็ยังส่งให้ผู้เช่าได้และไม่ push สรุป
- ลิงก์ QR/PDF ในข้อความสร้างจาก **origin ของ request เอง** (`new URL(c.req.url).origin`) ไม่ hardcode โฮสต์ production จึงใช้ได้ทั้ง workers.dev, custom domain และ local dev
- ถ้า origin ของ request ไม่ใช่ https เซิร์ฟเวอร์จะ log คำเตือน เพราะ LINE ปฏิเสธ URL รูปที่ไม่ใช่ https — เกิดเฉพาะตอน dev บน local http เท่านั้น
- Flex message ยึดโครงข้อความของ ticket 08: หัวข้อพื้นทึบ `#2563eb` ตัวอักษรขาว (`ใบแจ้งหนี้ / INVOICE` + `ห้อง … | ประจำเดือน …`), เนื้อมี `ผู้เช่า`, แถว `ออกบิลเมื่อ`, ค่าห้อง/น้ำ/ไฟ (หน่วย × อัตรา หรือ `เหมาจ่าย`) และค่าใช้จ่ายเพิ่มทุกรายการตามชื่อบนบิล, ยอดรวมตัวหนาสีแดง `#dc2626`; ท้ายมีรูป QR `/qr/:billId.png`, ปุ่ม `เปิดใบแจ้งหนี้ PDF` ไปที่ `/invoices/:billId.pdf` และบรรทัดบอกให้ส่งสลิปกลับในแชท — โมดูล builder อยู่ที่ `src/worker/line/bill-message.ts`

## สลิป และการปิดบิลอัตโนมัติ

ผู้เช่าส่งรูปสลิปการโอนกลับมาในแชทบอทเดียวกันได้ ระบบดาวน์โหลดรูป เก็บลง R2 ส่งให้ SlipOK ตรวจ และปิดบิลให้อัตโนมัติเมื่อยอดตรง สลิปที่ตรวจไม่ผ่านหรือยอดไม่ตรงจะถูกเก็บไว้ที่คิว "รอตรวจ" ให้เจ้าของตัดสิน

- **ดาวน์โหลดรูปจาก LINE** — `message` event ที่ `message.type = "image"` จะดึงรูปจาก data host `https://api-data.line.me/v2/bot/message/{messageId}/content` ด้วย bearer token (คนละ host กับ messaging API) รับเฉพาะ `content-type` `image/png`, `image/jpeg`, `image/webp` (อย่างอื่น เช่น `image/svg+xml` ถูกปฏิเสธ เพราะผู้ให้บริการตรวจสลิปอ่านได้เฉพาะ PNG/JPEG/WebP) และจำกัดขนาด 5 MiB โดยเช็ค `content-length` เมื่อมี พร้อมอ่านแบบมีขอบเขต (bounded read) กัน body ใหญ่เกินแม้ไม่ประกาศ header — เกิน/ผิดชนิด/ดาวน์โหลดไม่สำเร็จ = ตอบกลับเป็น Flex card สั้นๆ ว่าลองส่งใหม่ log แบบมีโครงสร้างหนึ่งบรรทัด และไม่เก็บอะไรลง R2/D1
- **คีย์รูปเป็นคีย์สุ่ม 128-bit** (`crypto.getRandomValues` เป็น hex 32 ตัว + `.png`) ไม่ได้มาจากบิล ผู้เช่า หรือ message id และไม่เดาได้ — รูปเดียวกันที่ส่งซ้ำจะได้คนละคีย์
- **`GET /slips/:imageKey.png` ต้องล็อกอินและเป็นครอบครัวเดียวกับสลิปนั้นเท่านั้น** (ไม่ใช่ route สาธารณะเหมือน `/qr/*`/`/invoices/*` อีกต่อไป) — ตรวจ session cookie ก่อน แล้วเช็คว่า `slips.family_id` ตรงกับครอบครัวที่ล็อกอินก่อนอ่านจาก R2; ไม่พบสลิปของครอบครัวนั้น คีย์ไม่มีใน R2 หรือชื่อไฟล์ไม่ใช่ `.png`/`.jpg`/`.jpeg` ตอบ `404` แบบเดียวกันหมด ไม่บอกใบ้ว่าคีย์มีอยู่จริงแต่เป็นของครอบครัวอื่น เสิร์ฟ bytes พร้อม content type ที่บันทึกไว้ตอนดาวน์โหลด (`image/png`/`image/jpeg`/`image/webp`) และ `cache-control: private, no-store` (รูปมีข้อมูลผู้เช่า/ยอดเงิน ห้ามแคชสาธารณะ)
- **`GET /slips/p/:imageKey.png?e=<epoch>&s=<hex>` เป็นลิงก์ที่เซ็นชื่อและมีอายุ** — ใช้เป็น URL ของปุ่ม "ดูสลิป" ในการ์ดแจ้งเจ้าของ เพราะเซิร์ฟเวอร์/เบราว์เซอร์ใน LINE เปิด `/slips/:file` ที่บังคับ session ไม่ได้ ลายเซ็นคือ HMAC-SHA256 ของ `` `${imageKey}.${expires}` `` ด้วย `SLIP_LINK_SECRET` (hex ตัวพิมพ์เล็ก) เทียบแบบ constant-time; `expires` เป็นวินาที epoch อายุ 7 วัน (`slipLinkTtlSeconds` ใน `src/worker/lib/slip-link.ts`); ลายเซ็นผิด/หมดอายุ หรือคีย์ไม่มีใน R2 → `404` (หมดอายุใช้ข้อความต่างหาก) ตอบ `cache-control: private, max-age=3600` แทน `no-store` เพื่อให้เบราว์เซอร์ในแอป LINE โหลดซ้ำ/ซูมได้ — **ยังไม่ตั้ง `SLIP_LINK_SECRET`** (ค่าว่าง) → `signedSlipUrl` คืน `null` การ์ดซ่อนปุ่มดูสลิปแต่ยังส่งได้ และ route ปฏิเสธทุกคำขอโดยไม่ throw (ตั้งค่าจริงด้วย `wrangler secret put SLIP_LINK_SECRET --env=''`)
- **route นี้อยู่นอก `/api/*`** จึงไม่ผ่าน middleware กลางใน `index.ts` — ตรวจ session และความเป็นเจ้าของเองใน `src/worker/routes/slips.ts` และยังต้องอยู่ใน `assets.run_worker_first` (ดูรายการท้ายหัวข้อนี้) ไม่งั้นจะได้ static asset/SPA แทน · `/slips/p/:file` เป็นสอง segment จึงไม่ชนกับ `/:file` ที่รับ segment เดียว
- **ตรวจสลิปด้วย SlipOK** — `POST https://api.slipok.com/api/line/apikey/{branchId}` เป็น `multipart/form-data` พร้อม header `x-authorization: <SLIPOK_API_KEY>` โดยแนบ bytes ของรูปเป็น part ชื่อ `files` (filename `slip.png`/`slip.jpg`/`slip.webp` และ content type ตามที่ดาวน์โหลดมา) บวกกับ `log=true` และ `amount=<ยอดบิลที่คาดไว้>` เป็นสตริงเมื่อมีบิลให้เทียบ — โค้ดไม่ตั้ง `Content-Type` เอง ปล่อยให้ runtime ใส่ multipart boundary; รูปสลิปจึงไม่ต้องเปิดให้เข้าถึงจากอินเทอร์เน็ตเพื่อให้ตรวจผ่าน ตัวไคลแอนต์เป็น fail-soft: ไม่มีคีย์/รหัสสาขา เรียกไม่สำเร็จ หรือตอบไม่ใช่ JSON → log แบบมีโครงสร้างและคืน `verified: false` ไม่ throw; ถือว่าตรวจผ่านเฉพาะ payload ที่ประกาศ `success: true` และมียอดในสลิปที่อ่านได้; รหัส `1012` (สลิปซ้ำ) ทำให้สลิปถูกปฏิเสธด้วย `duplicate_slip`, รหัส `1013` (ยอดไม่ตรง) ถือว่าสลิปจริงแต่ยอดต่างแล้วให้การเทียบของเราตัดสิน; payload อื่นถือว่าตรวจไม่ผ่าน (ไม่มีทางกลายเป็น "ยอดตรง")
- **ตัดสินจาก `code` ใน body ไม่ใช่สถานะ HTTP** — SlipOK ตอบ **HTTP 400 ให้ทุก error code ที่เป็นผลการตรวจ** (ยืนยันด้วยการยิงจริง: `1005`/`1007`/`1012`/`1014` → 400, `1002` → 401) จึงอ่าน payload แล้วเรียก `normalise` ก่อนเช็ค `response.ok` เสมอ ถ้าเช็ค status ก่อน รหัส `1012` จะไม่ถูกปฏิเสธเป็นสลิปซ้ำ รหัส `1014` (ผู้รับผิดบัญชี) จะไม่ถูกป้ายเป็น mismatch และ `transRef`/`amount` ที่ผู้ให้บริการอ่านได้จะถูกทิ้งทั้งที่เจ้าของหอต้องใช้เทียบกับใบเสร็จของธนาคาร — `response.ok` เป็นเพียงตัวช่วยตัดสินเมื่อ payload อ่านไม่ได้เลย (กรณีนั้นนับเป็น "ตรวจไม่ได้" ไม่ใช่ "สลิปไม่จริง")
- **เรียกตรวจไม่สำเร็จ ≠ สลิปไม่จริง** — `verifySlip` คืน `{result, failed, failure}` โดย `failed = true` เมื่อตรวจไม่ได้จริง ๆ: ไม่มีคีย์/รหัสสาขา รูปว่าง เรียกไม่สำเร็จ หรือผู้ให้บริการตอบรหัสที่บอกว่ายังตัดสินไม่ได้ (`1001`–`1004`, `1009`, `1010`) กรณีนี้สลิปเข้าคิวที่ reason **`verify_failed`** พร้อม `detail` บอกสาเหตุ เพื่อให้เจ้าของหอรู้ว่าต้องตรวจด้วยมือเพราะระบบตรวจไม่ได้ ไม่ใช่เพราะสลิปปลอม (ดูหัวข้อ "เหตุผลที่สลิปไม่ผ่าน")
- **ปิดบิลอัตโนมัติ** — เงื่อนไขครบทั้งสามข้อจึงปิดบิล: SlipOK ยืนยันว่าสลิปจริง (`success: true`), ยอดในสลิปเท่ากับ `total` ของบิล unpaid ล่าสุดของห้องผู้ส่ง (เทียบเป็นสตางค์ ไม่เทียบ float — `total` รวมค่าใช้จ่ายเพิ่มและครอบทั้งห้องมิเตอร์และห้องเหมาจ่ายเพราะอ่านจากแถวบิล), และไม่ใช่สลิปซ้ำที่ผู้ให้บริการรายงาน (รหัส `1012`) พร้อมกับที่ `transRef` (ถ้ามี) ไม่เคยถูกใช้ปิดบิลมาก่อน → บิลเป็น `paid` (`paid_method: 'transfer'`, `paid_at` เป็น ISO มาตรฐานที่แปลงจากวันที่บนสลิป ถ้าอ่านไม่ได้ใช้เวลาปัจจุบัน) + สลิปเป็น `matched` + push ยืนยันยอดและเดือนถึงผู้เช่า; การปิดบิลเป็น `UPDATE bills SET status = 'paid', … WHERE id = ? AND status = 'unpaid'` ถ้าไม่มีการเปลี่ยนแปลง (เจ้าของเพิ่งปิดบิลเอง) ถือว่าไม่มีบิลค้างและเก็บสลิปเป็น `pending_review`
- **สลิปหนึ่งใบปิดได้บิลเดียว** — บังคับด้วย partial unique index `idx_slips_matched_trans_ref` บน `slips(trans_ref)` เฉพาะแถว `status = 'matched'` ไม่ใช่แค่ `SELECT` ก่อนเขียน ดังนั้น webhook สองอันที่มาพร้อมกันปิดสองบิลด้วยเลขอ้างอิงเดียวกันไม่ได้; ส่งสลิปที่ **ปิดบิลไปแล้ว** ซ้ำอีกครั้งจะถูกบันทึกเป็น `rejected` และไม่ปิดบิลที่สอง — สลิปที่ยังไม่เคยปิดบิลส่งซ้ำได้ตามปกติ (ดูหัวข้อ "สลิปซ้ำต้องมีสองหลักฐาน" ด้านล่าง)
- **ยอดไม่ตรง / ตรวจไม่ผ่าน / ห้องยังไม่มีบิลค้าง** → สลิปเป็น `pending_review` เก็บ `bill_id` (บิลที่ถูกนำไปเทียบ), `bill_total` (ยอดบิลตอนเทียบ), `amount`/`trans_ref`/`verify_result` ไว้ให้เจ้าของตรวจ และ push ข้อความตรงไปตรงมาถึงผู้เช่า (ยังไม่ยืนยันว่าปิดบิล) — `verify_result.reason` เป็นคำศัพท์คงที่สำหรับคิวรอตรวจ: `mismatch | not_verified | no_unpaid_bill | duplicate_slip | verify_failed`; กรณีไม่มีบิลค้าง `bill_id`/`bill_total` เป็น NULL และ reason เป็น `no_unpaid_bill` — เหตุผลของแต่ละค่าถูกเก็บไว้ในตัวสลิปและแสดงในหน้ารอตรวจ (ดูหัวข้อ "เหตุผลที่สลิปไม่ผ่าน")
- **แจ้งเจ้าของทาง LINE** — ทุกครั้งที่สลิปถูกบันทึกเป็น `pending_review` ระบบ push ถึงเจ้าของ (`settings.owner_line_user_id`) หนึ่ง Flex card การ์ดเตือน ไม่มีเครื่องหมายอัศเจรีย์: แถวห้อง ชื่อผู้เช่า ยอดในสลิป และยอดบิลที่นำมาเทียบ (ถ้าไม่มีบิลค้างจะบอกว่า "ตอนรับสลิปไม่พบบิลค้าง" และถ้าอ่านยอดจากสลิปไม่ได้จะบอกว่า "อ่านไม่ได้") พร้อมบรรทัดเหตุผลว่าทำไมสลิปไม่ถูกปิดอัตโนมัติ (เช่น "ยอดในสลิปไม่ตรงกับยอดบิล" หรือ "ระบบตรวจสลิปกับผู้ให้บริการไม่สำเร็จ ต้องตรวจด้วยมือ" เมื่อเป็น `verify_failed`); ยังไม่เชื่อม LINE เจ้าของ = log หนึ่งบรรทัดแล้วทำงานต่อ (ไม่ error) และ push ที่ล้มเหลวไม่ทำให้ webhook พังหรือเปลี่ยนสถานะสลิป เพราะยิงหลังเขียน DB แล้วแบบ fail-soft — ข้อความอยู่ที่ `ownerSlipPendingMessage()` ใน `src/worker/line/messages.ts`
- **ผู้ส่งที่ยังไม่เชื่อม LINE** — ไม่ดาวน์โหลด ไม่เก็บรูป ไม่สร้างแถวสลิป ตอบกลับให้พิมพ์เลขห้องก่อนส่งสลิป
- บอทไม่ log ตัวรูปหรือ secret ใดๆ ลง log มีเฉพาะ identifier แบบมีโครงสร้าง (slip id, image key, bill id, userId)

### แจ้งเตือนเมื่อบิลถูกปิด (เจ้าของทาง LINE + เว็บแบบเรียลไทม์)

บิลเปลี่ยนเป็น `paid` ได้สามทาง และ**ทั้งสามทางยิงการแจ้งเตือนชุดเดียวกัน** ผ่านตัวส่งกลาง `src/worker/lib/paid-notify.ts`:

| ทาง | ต้นทาง | `source` | สลิป |
|---|---|---|---|
| A | `POST /api/bills/:id/mark-paid` (เจ้าของกดปิดเอง) | `mark-paid` | ไม่มี |
| B | `POST /api/slips/:id/resolve {action:"settle"}` | `owner-settle` | `slips.image_key` |
| C | สลิปยอดตรงปิดบิลอัตโนมัติจาก webhook (`handleSlipImage`) | `auto-slip` | คีย์ที่เพิ่งอัปโหลด |

- `markPaid()` ใน `src/worker/routes/demo.ts` เป็นการ seed ข้อมูลสาธิต **ไม่ยิงแจ้งเตือน**
- **ลิงก์ที่บอทส่งต้องเปิดนอกแอป LINE และต้องพาไปถึงที่หมายจริง** — ปุ่มใน Flex Message ถูกเปิดด้วย in-app browser ของ LINE เสมอ และ Google **ปฏิเสธ** คำขอ OAuth จาก embedded webview (ตอบ `disallowed_useragent` ตั้งแต่ ก.ค. 2023) ลิงก์ที่กดแล้วต้องผ่านการเข้าสู่ระบบด้วย Google จึงพังทันทีถ้าเปิดในแอป — `lineMessageUrl` เติม `openExternalBrowser=1` **เป็น query ก่อน fragment** (fragment ไม่ถูกส่งไปเซิร์ฟเวอร์ LINE จึงมองไม่เห็นถ้าไปต่อท้าย) ให้ทั้งลิงก์บิลและลิงก์คำเชิญ · **ลิงก์ลงทะเบียนผู้เช่าไม่เติมโดยเจตนา** เพราะหน้านั้นต้องอยู่ใน LINE เพื่อใช้ `liff.isInClient()` + access token ของ LIFF (มีเทสต์กันไว้) · `billDetailUrl` ต้องแนบ `period` ไปด้วยเสมอ: หน้ารายละเอียดหาบิลจากรายการที่โหลดตามรอบบิล (ค่าเริ่มต้นคือรอบปัจจุบัน) ลิงก์บิลเดือนก่อนที่ไม่มี period จึงขึ้น "ไม่พบบิลที่จะแสดง" ทั้งที่บิลมีอยู่
- **ที่หมายรอดข้าม Google OAuth** — fragment ของแอปทั้งหมด (`#bills/detail/…`, `#invite/…`) ไม่ถูกส่งไปเซิร์ฟเวอร์ จึงฝากในคุกกี้ `wangchan_google_next` ตอน `/api/auth/google/start?next=…` แล้ว callback เด้งกลับไปที่ fragment นั้น · `safeReturnPath` (ใช้ร่วมกันทั้ง worker และ client ผ่าน `src/shared/`) รับเฉพาะค่าที่ขึ้นต้นด้วย `#` เท่านั้น — fragment เปลี่ยน host/scheme ไม่ได้ไม่ว่าข้างในเป็นอะไร จึงกัน open redirect ได้ตั้งแต่ต้นทางโดยไม่ต้องไล่ห้าม `//` หรือ `:` (ซึ่งจะไปปฏิเสธ fragment ที่ถูกต้อง) ปฏิเสธแค่อักขระควบคุมเพราะค่านี้ถูกใส่ใน Location header · ล้มเหลวกลางทาง (กดยกเลิก/เลือกบัญชีผิด) ยังคงฝาก `next` ไว้ให้กดลองใหม่แล้วถึงบิลเดิม · หน้าเข้าสู่ระบบแนบ `?next=` ให้เองจาก hash ปัจจุบัน และฝั่ง client ย้าย `?next=` กลับเป็น fragment ด้วย `history.replaceState` (ไม่ reload) แล้วลบ query ทิ้ง · Worker เดโมผ่าน `next` ให้ `/api/demo/enter` ด้วยเหตุผลเดียวกัน
- **คนที่ติดอยู่ในเบราว์เซอร์ของ LINE** — ลิงก์ที่บอทส่งแก้แล้ว แต่คนที่จำ URL เองหรือกดลิงก์เก่ายังเจอ Google "Access blocked" · หน้าเข้าสู่ระบบและหน้าคำเชิญตรวจจับ `Line/` ใน user agent แล้วขึ้นกล่องเตือนพร้อมปุ่มคัดลอกลิงก์ให้เอาไปเปิดใน Safari/Chrome แทนการปล่อยให้กดปุ่มที่ไม่ทางสำเร็จ
- **LINE ถึงเจ้าของ** (`pushOwnerBillPaid`, เรียกผ่าน `c.executionCtx.waitUntil` ยกเว้นทาง C ที่ await เพราะอยู่ใน `waitUntil` ของ webhook อยู่แล้ว) — อ่าน `settings.owner_line_user_id` ถ้าว่างข้ามพร้อม log; การ์ด `ownerBillPaidMessage` (tone success, altText `ห้อง … ชำระบิล … แล้ว ยอด … บาท`) มีแถว ห้อง / ผู้เช่า / รอบบิล / ยอดชำระ (bold) / ช่องทาง / เวลาที่ชำระ และ footer ปุ่ม: มีสลิป → `ดูสลิป` (primary) + `เปิดบิลในเว็บ`, ไม่มีสลิปหรือยังไม่ตั้ง `SLIP_LINK_SECRET` → `เปิดบิลในเว็บ` ปุ่มเดียว; ช่องทางแสดงเป็น `สลิปอัตโนมัติ` / `ยืนยันจากคิวรอตรวจ` / `เงินสด` / `โอน (บันทึกเอง)` (`methodLabel`); เวลาเป็น `toLocaleString("th-TH", { timeZone: "Asia/Bangkok" })` (`paidAtLabel`)
- **WebSocket ถึงทุกแท็บเว็บ** (`broadcastBillPaid`) — หนึ่ง Durable Object ต่อครอบครัว (`FamilyRealtime` ใน `src/worker/realtime.ts`, ผูก `env.REALTIME`) เก็บเฉพาะ socket ที่เปิดอยู่ ไม่มี state ถาวรและ**ไม่มี replay buffer โดยตั้งใจ**: ไม่มีแท็บเปิด = event หายไป ฝั่งเว็บจึงถือว่า "ต่อกลับมา" คือสัญญาณให้โหลดข้อมูลหน้าใหม่
  - handshake: `GET /api/realtime` ผ่าน `requireAuth` ของ `/api/*` (ไม่มี cookie = `401`), รับเฉพาะ `Upgrade: websocket` (ไม่งั้น `426`), ตรวจ `Origin` เองเพราะ `sameOriginOnly` ครอบเฉพาะ method ที่เปลี่ยนข้อมูล (`403` เมื่อ origin แปลก), แล้วส่งต่อให้ DO ด้วย `idFromName(familyId)`
  - ใช้ `ctx.acceptWebSocket` (ไม่ใช่ `server.accept()`) เพื่อให้ DO hibernate ได้ และตั้ง `WebSocketRequestResponsePair("ping", "pong")` ให้ตอบ ping โดยไม่ปลุก DO; `broadcast(payload, excludeConnectionId)` ข้าม socket ต้นทาง (กัน toast ซ้ำ) และ `try/catch` ต่อ socket เพื่อไม่ให้ตัวที่ตายแล้วล้มทั้ง loop
  - envelope เดียวที่ทุก event ใช้ร่วมกัน: `{v: 1, type: "hello", connectionId}`, `{v: 1, type: "bill-paid", …}` และ `{v: 1, type: "tenant-joined", tenantId, roomNumber, tenantName, source, joinedAt}` — ขยายชนิดใหม่ได้โดยไม่ต้องแก้ client เก่า (client กรองด้วย `type` และตรวจชนิดของทุกฟิลด์ก่อนใช้)
- **แจ้งเตือน "มีผู้เช่าใหม่"** (`broadcastTenantJoined`) — ยิงจากสองทางที่ผู้เช่าเข้าระบบ และ **`source` แยกสองทางนั้น** เพราะการกระทำที่เจ้าของต้องทำต่อต่างกัน:
  - `self` = ลงทะเบียนเองผ่านฟอร์ม LIFF (`/api/register`) → เจ้าของยังไม่รู้จักคนนี้ ต้องเข้าไปดูว่าตั้งไว้ถูกไหม
  - `owner` = เจ้าของกดเชื่อม LINE ให้ผู้เช่าที่มีอยู่แล้ว (`/api/line/pending/:id/link`) → เจ้าของทำเองแล้ว แค่ยืนยันว่าเชื่อมติด
  - **ไม่รับ `excludeConnectionId`** ต่างจาก `broadcastBillPaid` เพราะไม่มี "แท็บต้นทาง" ให้ยกเว้น: การลงทะเบียนเกิดจากอุปกรณ์ของผู้เช่า และการเชื่อม LINE เป็นการกระทำที่เจ้าของควรเห็นผลในทุกแท็บรวมทั้งแท็บที่กด
  - ฝั่งเว็บเพิ่ม `tenantsChangedEvent` ให้หน้าผู้เช่าและแดชบอร์ดโหลดใหม่ (เดิมฟังแค่ `billsChangedEvent` หน้าผู้เช่าจึงไม่มีทางเห็นคนใหม่) — แดชบอร์ดนับจำนวนห้องว่างจากข้อมูลชุดเดียวกันจึงต้องรีเฟรชด้วย
  - กระดิ่งใช้ `person_add` (สีน้ำเงิน accent) ต่างจาก `check_circle` ของการชำระ เพื่อแยกสองเหตุการณ์ด้วยสายตา และลิงก์ไป `#tenants` (ผู้เช่าไม่มีหน้าของตัวเองให้เปิดตรง ๆ)
- **ปุ่มแจ้งเตือนบนแถบบน (กระดิ่ง)** — เดิมเป็นปุ่มเปล่าใน `design/index.html` ตอนนี้เป็นที่เก็บรายการ "บิลถูกปิด" ที่รับทาง WebSocket ระหว่างที่แท็บเปิดอยู่ (`src/client/notifications.ts` + `notification-button.tsx`) · เก็บในหน่วยความจำของแท็บเท่านั้น **ไม่เก็บลง sessionStorage โดยตั้งใจ** เพราะรายการเหล่านี้หมดความหมายหลังรีเฟรช (ของจริงอยู่ในหน้าบิล) และข้อมูลเก่าที่ค้างอยู่จะทำให้ตัวเลขไม่ตรงกับบิล · กันรายการซ้ำด้วย `billId` (socket ที่ต่อใหม่รับข้อความเดิมซ้ำได้) และจำกัด 50 รายการกันแท็บที่เปิดค้างทั้งวันกินหน่วยความจำโตไม่จำกัด · เปิดแผง = อ่านทั้งหมด (`notifications_active` → `notifications` + ตัวเลขบนปุ่มหาย) และแต่ละรายการเป็นลิงก์ไป `#bills/detail/<id>?period=<period>` พร้อมปิดแผงเมื่อกด
  - **Toast ยังอยู่คู่กับกระดิ่ง** ไม่ได้แทนกัน: toast บอกทันทีโดยไม่ต้องกดปุ่ม กระดิ่งกันกรณี "ไม่ได้จ้องจอตอนนั้น" (toast หายใน 5 วินาที) · ทั้งคู่ใช้ข้อความบรรทัดเดียวกันจาก `notificationText` เพื่อไม่ให้พูดไม่ตรงกัน
  - ตำแหน่งแผงต่างกันตามจอ **โดยตั้งใจ**: จอใหญ่ยึดขวาของปุ่ม (ปุ่มอยู่ชิดขวา), จอเล็กยึดขอบจอ (`fixed left-3 right-3`) เพราะปุ่มอยู่ซ้ายถัดจากโลโก้ — ลองยึดซ้ายของปุ่มแล้วล้นออกนอกจอ 24px และยึดขวาก็ล้นไปทางซ้าย 250px จึงยึดกับ viewport แทนซึ่งไม่มีทางล้นไม่ว่าปุ่มจะอยู่ตรงไหน (วัดจริงที่ 390px: panel อยู่ 12–378 พอดีในจอ)
- **ฝั่งเว็บ** — `src/client/realtime.ts` (`startRealtime`) ต่อ `wss://<host>/api/realtime` เก็บ `connectionId` จาก `hello` แล้ว `src/client/api.ts` แนบ header `x-realtime-id` ให้ทุกคำขอที่เปลี่ยนข้อมูล เซิร์ฟเวอร์จึงบอก DO ให้ข้ามแท็บต้นทางได้; backoff `[1s, 2s, 4s, 8s, 30s]` เลื่อนขั้นละหนึ่งต่อการหลุดหนึ่งครั้ง (กัน `error`+`close` ที่ยิงคู่กันนับซ้ำ) รีเซ็ตเมื่อ `onopen`, ping ทุก 30 วินาที, และ `visibilitychange` → ต่อใหม่ทันทีเมื่อกลับมาเปิดแท็บแล้ว socket ไม่ OPEN; `App.tsx` เด้ง `Toast` กลาง 5 วินาที (`ห้อง … ชำระแล้ว … บาท`) แล้วประกาศ `billsChangedEvent`/`reviewQueueChangedEvent` ให้หน้าปัจจุบันโหลดใหม่ — แดชบอร์ด `src/client/pages/dashboard.tsx` ฟัง `billsChangedEvent` จึงอัปเดตตัวเลขเองโดยไม่ต้องรีเฟรช
- **การปิดบิลต้องไม่ล้มเพราะการแจ้งเตือน** — `broadcastBillPaid` ครอบ `try/catch` ทั้งก้อนและ `pushOwnerBillPaid` จบที่ `logLineFailure`; บิลถูกเขียนเป็น `paid` ไปแล้วก่อนถึงขั้นนี้ คำขอจึงตอบ `200` เสมอแม้ LINE หรือ DO มีปัญหา (ถ้าปล่อยให้เป็น 500 ผู้ใช้จะเข้าใจว่าปิดไม่สำเร็จแล้วกดซ้ำ ซึ่งได้ `409`)

### คิวรอตรวจ (API สำหรับหน้า "รอตรวจ")

สอง endpoint นี้อยู่หลังการล็อกอิน (เหมือน `/api/*` อื่น ๆ) และเป็นข้อมูลที่หน้า "รอตรวจ" ใช้ทั้งหมด (`src/worker/routes/slips-admin.ts`) ส่วน route รูป `/slips/{file}` ก็ต้องล็อกอินและเป็นครอบครัวเดียวกันเช่นกัน (ดูหัวข้อ "สลิป และการปิดบิลอัตโนมัติ" ด้านบน) ไม่ใช่ route สาธารณะอีกต่อไป

- `GET /api/slips?status=&billId=` — เรียงใหม่สุดก่อน; **ไม่ส่ง `status` เลย = เฉพาะ `pending_review`** เพราะตัว endpoint นี้คือคิว (ถ้าส่ง `billId` แต่ไม่ส่ง `status` จะคืนทุกสถานะของบิลนั้น = ประวัติของบิล ไม่ใช่คิว); `status` รับ `pending_review | matched | rejected` ค่าอื่น `400` `field: "status"`; ส่ง `billId` คู่กับ `status` ได้; ดูบิลของสลิปด้วย `LEFT JOIN` ครั้งเดียวต่อสลิป
- payload ต่อสลิป (camelCase, `{ok: true, slips: [...]}`):

  ```json
  {
    "id": "…",
    "createdAt": "2026-09-03 03:15:12",
    "imageKey": "8f2c…c1.png",
    "imageUrl": "/slips/8f2c…c1.png",
    "status": "pending_review",
    "reason": "mismatch",
    "slipAmount": 3550.5,
    "bill": { "id": "…", "roomNumber": "A101", "tenantName": "สมชาย ใจดี", "period": "2026-09", "total": 3550 },
    "verified": true,
    "verify": { "verified": true, "transRef": "014112345678901", "date": "2026-09-03T10:15:00+07:00", "code": null, "message": null, "detail": null },
    "transferAt": "2026-09-03T10:15:00+07:00"
  }
  ```

  - `imageUrl` = path `/slips/{imageKey}` ที่ต้องมี session cookie ของครอบครัวเดียวกับสลิปนั้นจึงจะเห็นรูปได้ (ไม่ใช่สาธารณะ — browser ส่ง cookie ให้เองเพราะเป็น same-origin `<img>`), `reason` = `verify_result.reason` (คำศัพท์คงที่), `slipAmount` = ยอดในสลิป (`NULL` เมื่ออ่านไม่ได้), `verified`/`verify` มาจากผลตรวจที่บันทึกไว้, `transferAt` = วันที่จากผู้ให้บริการ (เท่ากับ `verify.date`) ใช้เทียบ "วันเวลาโอน" ในหน้ารายละเอียด
  - `bill.total` = `slips.bill_total` ซึ่งเป็นยอดบิล **ณ ตอนที่นำสลิปไปเทียบ** (fallback ยอดบิลปัจจุบันเฉพาะกรณีที่ไม่มีค่าเก็บไว้) ส่วนชื่อห้อง/ผู้เช่า/เดือนมาจาก join กับ `bills`/`rooms`/`tenants`; `bill` เป็น `null` เมื่อตอนบอทรับสลิปห้องนั้นไม่มีบิลค้างให้เทียบเลย — "บิลถูกลบไปแล้ว" ไม่ทำให้เกิดสภาพนี้ได้ เพราะ FK จาก `slips.bill_id` ห้ามลบบิลที่สลิปอ้างถึง ส่วนกรณีบิลถูกปิดไปก่อนระหว่างตรวจสลิป `bill` ยังมีค่า (ดูหัวข้อ "สลิปที่ไม่มีบิลค้างให้เทียบ") — ตอนตัดสินส่ง `billId` มาเองได้
  - สลิปที่ `matched` ยังเก็บ `reason` เดิมไว้ (เหตุผลที่สลิปเคยเข้าคิว) เพราะการปิดบิลจากคิวไม่ลบข้อมูลที่บันทึกไว้; สลิปที่ `rejected` มี `decision`/`decidedAt` เพิ่มใน `verify_result` ส่วนสลิปที่ปิดอัตโนมัติจากยอดตรงไม่มี `reason` เลย (`null`)
- `POST /api/slips/:id/resolve {action: "settle" | "reject", billId?}` — ตอบ `200 {ok: true, slip}` พร้อม payload ล่าสุดของสลิป (รูปเดียวกับข้างบน); สลิปที่ไม่รู้จัก `404`, สลิปที่ตัดสินไปแล้ว `409 CONFLICT`, `action` อื่น `400 field: "action"`
  - `settle` — บิลเป้าหมาย = `billId` ใน body ?? `bill_id` ของสลิป (ไม่มีทั้งคู่ `400 field: "billId"`); บิลต้องมีอยู่ (`404`) และยัง `unpaid` (`409`); `trans_ref` ของสลิปต้องไม่ถูกใช้ปิดบิลไปแล้ว (`409` — ตรวจก่อนเขียนและกันซ้ำด้วย partial unique index อีกชั้น) จากนั้น `DB.batch` เดียว: บิลเป็น `paid` (`paid_method: 'transfer'`, `paid_at` = วันที่บนสลิปเมื่อใช้ได้ ไม่งั้นใช้เวลาปัจจุบัน และมีเงื่อนไข `AND status = 'unpaid'`) + สลิปเป็น `matched` พร้อม `bill_id`/`bill_total` ของบิลนั้น แล้ว push ยืนยันถึงผู้เช่าด้วยข้อความเดียวกับตอนปิดบิลอัตโนมัติ (`slipMatchedMessage`); ถ้าบิลเพิ่งถูกปิดไปก่อนหน้าจะคืน `409` และคืนสถานะสลิปกลับเป็น `pending_review` ตามเดิม
  - `reject` — สลิปเป็น `rejected` บิลไม่เปลี่ยนอะไร และ **ไม่ push อะไรเลย**; บันทึกการตัดสินไว้ใน `verify_result` (`decision: "rejected"` + `decidedAt` เป็น ISO) โดยคงผลตรวจและ `reason` เดิมไว้
  - สลิปที่ตัดสินแล้วหายจากคิว (badge ของเมนูนับจากความยาวของ list ปกติ) แต่ยังดูย้อนหลังได้ด้วย `?billId={billId}`

## QR พร้อมเพย์ และใบแจ้งหนี้ PDF

สอง route นี้เป็น **สาธารณะจริง ไม่ต้องล็อกอิน** เพราะลิงก์ถูกส่งไปในข้อความ LINE ของผู้เช่า — อย่าเพิ่มการบังคับล็อกอินกับสอง path นี้ และทั้งคู่ถูกใส่ใน `assets.run_worker_first` แล้ว จึงวิ่งเข้า Worker เสมอ

- `GET /qr/:billId.png` — รูป QR พร้อมเพย์ของบิลนั้นเป็น PNG (`image/png`, `cache-control: public, max-age=60`) payload เป็น EMVCo/PromptPay ตามมาตรฐาน: พร้อมเพย์ไอดีและประเภทจาก `settings` (`phone` → sub-tag `01` รูปแบบ `0066xxxxxxxxx`, `citizen-id` → sub-tag `02` เลข 13 หลัก), ยอด = `total` ของบิล (รวมค่าใช้จ่ายเพิ่ม) ทศนิยม 2 ตำแหน่ง, สกุลเงิน `764` (THB), ประเทศ `TH` และ CRC16-CCITT (FALSE) ปิดท้าย; ยอดอ่านจากแถวบิลทุกครั้งที่เรียก แก้บิลแล้วรูปเปลี่ยนตาม; ไม่พบบิล `404` เป็น JSON; ยังไม่ได้ตั้ง `promptpay_id` ตอบ `500` (ไม่ยอมสร้าง QR ไปบัญชีอะไรก็ไม่รู้)
- `GET /invoices/:billId.pdf` — ใบแจ้งหนี้ PDF สร้างสดจาก D1 ทุกครั้ง (`application/pdf`, `cache-control: no-store`, `content-disposition: inline; filename="B2569-09-A101.pdf"`) — ไม่มีไฟล์เก็บใน R2 และไม่มีความล้าสมัยของแคช; เนื้อหาตามโครงเอกสารใบแจ้งหนี้: เลขที่ (derive แบบเดียวกับ UI `B<พ.ศ.>-<MM>-<roomNumber>`), วันที่ออก (จาก `created_at`), ชื่อหอ/เจ้าของ/พร้อมเพย์, ห้อง · ผู้เช่า, ประจำเดือน, เลขมิเตอร์น้ำ/ไฟ, ตารางรายการ (ค่าห้อง, ค่าน้ำ หน่วย × อัตรา, ค่าไฟ หน่วย × อัตรา หรือเหมาจ่าย, ค่าใช้จ่ายเพิ่มทุกบรรทัดตามชื่อจริงบนบิล), ยอดรวมทั้งสิ้น และท้ายเอกสารฝังรูป QR พร้อมเพย์ของบิลพร้อมบรรทัดบอกผู้เช่าให้ส่งสลิปกลับในแชท LINE; ยอดเงินอ่านจาก snapshot ในแถวบิลเสมอ; ไม่พบบิล `404` เป็น JSON
- ตัวเลขและฟอนต์: ทั้งสอง route ใช้ `src/worker/lib/` (payload พร้อมเพย์ + CRC16, ตัวเขียน PNG, ตัวสร้างเอกสาร, ตัวเรนเดอร์ PDF) — ฟอนต์ไทยฝังใน Worker ด้วย Wrangler module rule ชนิด `Data` สำหรับ `**/*.ttf` (`src/worker/fonts/IBMPlexSansThai-Regular.ttf` + `-Bold.ttf` จาก Google Fonts, สัญญาอนุญาต SIL OFL 1.1 ดู `src/worker/fonts/OFL.txt`) แล้ว embed ด้วย `pdf-lib` + `@pdf-lib/fontkit` แบบ subset — ฟอนต์นี้มีทั้งไทยและละติน/ตัวเลขในไฟล์เดียว จึงพิมพ์เลขที่ใบแจ้งหนี้กับยอดเงินได้ครบ (Noto Sans Thai รุ่น static ไม่มี glyph ละติน ใช้กับเอกสารที่มีตัวเลขไม่ได้); ตอน embed ปิดฟีเจอร์ `ccmp` ของฟอนต์เพื่อให้ Thai Sara Am คงรูปประกอบ (U+0E33) ทำให้ text layer ของ PDF (`pdftotext`/คัดลอกข้อความ) ได้ `ประจำเดือน` `มิเตอร์น้ำ` `ค่าน้ำ` ตรงกับต้นฉบับ ไม่ซ้ำสระ

## แดชบอร์ด

`GET /api/stats/dashboard?period=YYYY-MM` (อยู่หลังการล็อกอิน เหมือน `/api/*` อื่น) คืนข้อมูลทั้งหน้าแดชบอร์ดของเดือนที่เลือกเป็น `{ok: true, period, kpis, revenue, unpaidBills, rooms}`; `period` บังคับและตรวจด้วย regex เดียวกับ route บิล (`^\d{4}-(0[1-9]|1[0-2])$`) ผิดหรือไม่ส่ง = `400 field: "period"`; อ่านข้อมูลด้วย query แบบ bounded 6 คำสั่ง (ห้อง+บิลของเดือนนั้น, บิลของเดือนนั้น, สลิป `pending_review` ของเดือนนั้น, ผลรวมบิลจ่ายแล้ว 6 เดือน, งวดล่าสุดที่มีบิล, บิลค้างของงวดก่อน ๆ ทุกห้อง) ไม่วน query ต่อห้อง

- `kpis` — `bills` (จำนวนบิลของเดือนนั้น), `dueAmount` (ผลรวม `total` ของบิลเดือนนั้น), `collectedAmount` (ผลรวมบิลที่จ่ายแล้ว), `unpaidAmount` (ผลรวมบิลที่ยังไม่จ่าย), `unpaidRooms` (จำนวนห้องที่มีบิลค้าง), `vacantRooms` (ห้องที่ไม่มีผู้เช่าปัจจุบัน), `totalRooms` (ทุกห้อง), `sentCount` (บิลที่มี `sent_at`) และ `paidCount` (บิลที่จ่ายแล้ว)
- `revenue` — 6 เดือนล่าสุดจบที่เดือนที่เลือก (ใหม่สุดอยู่ท้าย) เดือนละ `{period, amount}` โดย `amount` = ผลรวมบิลที่ **จ่ายแล้ว** ของเดือนนั้น และเติมเดือนที่ไม่มีบิลเป็น `amount: 0` เสมอ กราฟจึงมีหกแท่งครบ
- `unpaidBills` — บิลค้างของเดือนนั้น เรียงเก่าสุดก่อน (`created_at` แล้วตามด้วยเลขห้อง) แต่ละใบมี `{id, roomNumber, tenantName, total, createdAt, sentAt, hasPendingSlip}` โดย `hasPendingSlip` = มีสลิป `pending_review` ผูกกับบิลนั้น (สัญญาณว่าเจ้าของยังต้องตรวจ)
- `rooms` — ทุกห้อง เรียงตามเลขห้อง แต่ละห้อง `{id, roomNumber, status: "paid" | "unpaid" | "unbilled" | "vacant", hasPendingSlip, lastBilledPeriod, behindPeriods, arrears}` โดย `status` ตัดสินจากบิลของเดือนที่เลือก: ไม่มีผู้เช่าปัจจุบัน → `vacant`, ยังไม่ออกบิลเดือนนี้ → `unbilled`, บิลจ่ายแล้ว → `paid`, บิลค้าง → `unpaid`; `hasPendingSlip` ของห้องมาจากสลิป `pending_review` ของบิลเดือนนั้น; `behindPeriods` = จำนวนเดือนที่ห้องยังไม่ได้ออกบิลนับจาก `latestBilledPeriod` และ `arrears` = `{periods, amount}` ของบิล **ค้างของงวดก่อน ๆ** (`period < เดือนที่ดูอยู่`)

  `behindPeriods` กับ `arrears` ตอบคนละคำถามและต้องมีทั้งคู่: ห้องที่ค้างเงินงวดก่อนแต่เดือนนี้เพิ่งออกบิลแล้วจะมี `behindPeriods = 0` (ไม่ได้ "ตามหลัง" การออกบิล) แต่ `arrears.periods` ไม่ว่าง — ถ้ามีแต่ `behindPeriods` เงินที่ค้างจะหายไปจากสายตาเจ้าของหอทันทีที่ออกบิลใหม่ งวดที่กำลังดูอยู่เองไม่ถูกนับเป็น arrears

## นโยบายการคิดเงินรายเดือน

- **ปัดเศษขึ้นเสมอ (round up)** — ค่าน้ำและค่าไฟคิดจาก `หน่วย × อัตรา` แล้วปัดขึ้นเป็นบาทถ้วนด้วย `chargeFromUnits` ใน `src/shared/billing.ts` ไม่ว่าทศนิยมจะเท่าไร (30.39 → 31, 31.25 → 32) ยอดเหมาจ่ายที่กรอกก็ปัดขึ้นเช่นกัน เดิมทั้ง worker และหน้าเว็บปัดครึ่ง (`Math.round`) ทำให้เศษจากอัตราที่มีทศนิยมถูกปัดลงครึ่งหนึ่งของเวลา ขณะที่หอเก็บเงินเป็นบาทถ้วนและไม่รับภาระเศษที่เกิดจากอัตราของตัวเอง · **ไฟล์กลางนี้เป็นที่เดียวที่นิยามสูตร** เพื่อให้ยอดที่ผู้ใช้เห็นตอนกรอก (คำนวณในเบราว์เซอร์) ตรงกับยอดที่บันทึก (คำนวณใน worker) เสมอ — ก่อนหน้านี้มี 6 จุดที่เขียนสูตรซ้ำ · `migrations/0012_round_charges_up.sql` ปรับบิลที่ยังไม่จ่ายให้ตรงกฎใหม่ (บิลที่จ่ายแล้วไม่แตะ เพราะเป็นการตกลงราคาที่เกิดขึ้นจริงกับผู้เช่าไปแล้ว; D1 ไม่มีฟังก์ชัน `ceiling()` จึงปัดขึ้นด้วย `CAST(... AS INTEGER) + (x > CAST(...))`)
- **คิดบิลเป็นเดือนต่อเดือน** — บิลค้างของงวดก่อนเป็นเพียงข้อมูลที่ต้องบันทึกไว้ ไม่ใช่เงื่อนไขที่กันการออกบิลงวดใหม่ ห้องที่ค้างหลายงวดยังออกบิลเดือนถัดไปได้ตามปกติ และเลขมิเตอร์ตั้งต้นมาจากใบของงวดก่อนหน้าที่ใกล้ที่สุด (`loadLatestReadings` เลือก `MAX(period) < งวดที่กำลังออก` ต่อห้อง) จึ…
- **โอนมาเป็นยอดของงวดเก่า → ยึดบิลล่าสุด** — `handleSlipImage` เลือกบิลเป้าหมายด้วย `WHERE ... AND status = 'unpaid' ORDER BY period DESC LIMIT 1` (บิลค้างใหม่สุดของห้อง+ผู้เช่ารายนั้น) เสมอ ไม่ย้อนไปปิดงวดเก่าตามยอดที่ตรง เพราะยอดรายเดือนของหอใกล้งกันจนแยกไม่ออกจากตัวเลขเพียงอย่างเดียว
- **สลิปที่ไม่มีบิลค้างให้เทียบ** — เข้าคิวด้วย reason `no_unpaid_bill` — "บิลถูกลบไปแล้ว" **ไม่ใช่สาเหตุที่เกิดได้**: `slips` มี `FOREIGN KEY (family_id, bill_id) REFERENCES bills(family_id, id)` จึงลบบิลที่มีสลิปอ้างถึงไม่ได้ (ตอบ `409` พร้อมบอกให้ตัดสินสลิปให้จบก่อน) เหลือสองสาเหตุจริง: (ก) ตอนบอทรับสลิปห้องนั้นไม่มีบิลค้าง → `bill_id` เป็น NULL และ (ข) บิลที่เทียบไว้ถูกปิดด้วยทางอื่นระหว่างที่สลิปกำลังถูกตรวจ → **`bill_id` ยังอยู่** เพื่อให้เจ้าของหอเห็นว่าสลิปนี้ตั้งใจจะปิดใบไหน ทั้งสองกรณียังปิดบิลจากหน้าคิวไม่ได้เพราะ ณ ตอนตัดสินไม่มีบิลค้างเหลือ

## เหตุผลที่สลิปไม่ผ่าน แสดงในหน้ารอตรวจ

คำถามที่เจ้าของหอต้องตอบเวลาสลิปเข้าคิวคือ "ทำไม" — คำตอบเดิมมีแค่ป้าย "ตรวจไม่ผ่าน" ซึ่งไม่บอกอะไรเลย จึงเก็บเหตุผลจริงไว้ในตัวสลิปเอง (`slips.verify_result`) แล้วให้หน้ารอตรวจแสดง ไม่มีตารางหรือหน้าใหม่

- `verify_result.reason` มีห้าค่า: `mismatch` (ยอดไม่ตรง) · `not_verified` (ตรวจแล้วไม่ผ่าน) · `no_unpaid_bill` (ตอนรับสลิปไม่พบบิลค้าง) · `duplicate_slip` (สลิปซ้ำ) · **`verify_failed`** (ระบบตรวจไม่ได้)

### สลิปซ้ำต้องมีสองหลักฐาน ไม่ใช่แค่คำพูดของผู้ให้บริการ

**สลิปซ้ำ = บิลถูกปิดไปแล้ว + ผู้ให้บริการยืนยันว่าซ้ำ** ต้องครบทั้งสอง ถ้าขาดอย่างใดอย่างหนึ่งห้ามเรียกว่าซ้ำ

เหตุผล: `log=true` ทำให้ผู้ให้บริการจำรูปที่เคยเห็นได้ แต่ "จำได้" ไม่เท่ากับ "เงินถูกใช้ปิดบิล" สลิปที่ผู้ให้บริการอ่านไม่ได้รอบแรกแต่เราอ่านได้ (หรือยอดไม่ตรงแล้วเข้าคิว) จะถูกเก็บ `trans_ref` ไว้ พอโอนมาอีกรอบ เงื่อนไขเดิม `status <> 'rejected'` เห็นแถวที่ยัง `pending_review` แล้วตัดสินว่าเป็นสลิปซ้ำ — ผู้เช่าถูกปฏิเสธทั้งที่ยังไม่มีบิลใบไหนถูกปิด

- **ซ้ำจริง** — มีแถว `matched` ที่ `trans_ref` ตรงกัน → สลิปใหม่เป็น `rejected`, บันทึก `verify_result.usedSlipId` ชี้ใบที่ปิดบิลไปแล้ว, ข้อความผู้เช่า "สลิปนี้ถูกใช้ปิดบิลไปแล้ว"
- **provider บอกซ้ำแต่ยังไม่ปิดบิล** — เข้าคิว `pending_review` ที่ reason `duplicate_slip` พร้อมเก็บ `transRef`/`amount`/`code`/`message` จาก payload และข้อความผู้เช่าเป็น "ระบบเคยเห็นสลิปใบนี้แล้ว แต่ยังไม่พบบิลที่ปิดด้วยสลิปนี้" — **ห้ามปิดบิลอัตโนมัติ** เพราะผู้ให้บริการยังไม่ยืนยันว่าสลิปใบนี้ผ่าน และ**ห้ามปฏิเสธทิ้ง** เพราะเงินอาจโอนมาจริงแต่ยังไม่ถูกใช้ปิดบิล
- ทุกจุดที่เรียก "ซ้ำ" ใช้ `status = 'matched'` เท่านั้น (`handleSlipImage` ก่อน batch, หลัง batch, และเส้นทาง unique violation ซึ่งดึง `usedSlipId` มาให้ครบ)
- `normalise` แขน `1012` เก็บ `transRef`/`amount`/เวลา จาก `data` แทนที่จะทิ้ง — payload ของ 1012 มีข้อมูลครบเหมือนสลิปปกติ การทิ้งค่าทำให้ข้อความ "ถูกใช้ปิดบิลไปแล้ว" เป็นคำกล่าวอ้างที่ตรวจสอบไม่ได้
- **ด่านสุดท้ายยังอยู่**: partial unique index `idx_slips_matched_trans_ref` บน `(trans_ref) WHERE status = 'matched'` กันโอนครั้งเดียวปิดสองบิลแม้ webhook มาพร้อมกัน — ไม่ได้แตะ
- หน้ารอตรวจมีแท็บ "สลิปซ้ำ" และป้าย "สลิปซ้ำ (ยังไม่ปิดบิล)" เพื่อไม่ให้สับสนกับสลิปซ้ำของจริงที่ถูกปฏิเสธไปแล้ว
- `verify_result.code` / `verify_result.message` = รหัสและข้อความจากผู้ให้บริการตามที่ส่งมา (เช่น `1007` / "รูปภาพไม่มี QR Code") และ `verify_result.detail` = เหตุผลเชิงเทคนิคเมื่อตรวจไม่ได้ (เช่น `status 503`)
- หน้ารอตรวจแสดงเหตุผลใต้แถวผลตรวจเป็นข้อความอ่านรู้เรื่อง — `ตรวจไม่ผ่าน (1007): รูปภาพไม่มี QR Code` หรือ `ตรวจไม่ได้: status 503` — พร้อมกรองด้วยแท็บ "ตรวจไม่ได้" แยกจาก "ตรวจไม่ผ่าน"
- **`verify_failed` ≠ `not_verified`** — ตัวแรกคือเรายังไม่ได้คำตอบ (คีย์หาย ผู้ให้บริการล่ม ธนาคารยังไม่พร้อม) ซึ่งลองใหม่แล้วอาจผ่าน ส่วนตัวหลังคือคำตอบแน่ชัดว่ารูปนี้ใช้ปิดบิลไม่ได้ ทั้งสองกรณียังเข้าคิวเหมือนกันและบิลไม่ถูกแตะ แต่เจ้าของหอต้องทำคนละอย่าง จึงต้องแยกให้เห็น
- การแยกใช้ `providerIssueCodes` (`1001`–`1004`, `1009`, `1010`) บวกกับกรณีที่ไม่มีรหัสตอบกลับมาเลยพร้อม HTTP ที่ไม่สำเร็จ — **ไม่ใช้ `response.ok`** เพราะ SlipOK ตอบ HTTP 400 ให้ทุกผลการตรวจ `1007` (ไม่มี QR) จึงต้องนับเป็น "ตรวจแล้วไม่ผ่าน"
- ข้อความแจ้งเจ้าของทาง LINE แนบเหตุผลเดียวกันไปด้วย (`user/ownerSlipPendingMessage`) เจ้าของจะได้รู้ตั้งแต่ในการแจ้งเตือน ไม่ต้องเปิดหน้าเว็บก่อน
- งานที่รันเบื้องหลังและล้มเหลวโดยไม่มีสลิปให้ผูก (เช่น LINE ส่ง event ที่เขียน DB ไม่ได้) ยังจบที่ log แบบมีโครงสร้างตามเดิม — ไม่เก็บลงตารางใหม่ เพราะไม่มีที่ให้แสดงและไม่มีใครอ่าน


## LINE bot

- `POST /webhook/line` เป็น path สาธารณะ (ไม่ต้องล็อกอิน) ตรวจ `X-Line-Signature` แบบ HMAC-SHA256 จาก raw body ก่อนทุกอย่าง ถ้า signature ไม่ถูกต้องตอบ `403` และไม่แตะฐานข้อมูล
- event `follow` → บอททักทายและขอเลขห้อง; ข้อความ text ที่ตรงกับเลขห้องของผู้เช่าปัจจุบันที่ยังไม่เชื่อม → ผูก `tenants.line_user_id`; ข้อความที่ตรงกับรหัส 6 หลักใน `settings.owner_link_code` → บันทึก `settings.owner_line_user_id`; ข้อความอื่น → เก็บในตาราง `line_pending` ให้เจ้าของจับคู่เอง
- **การเชื่อม LINE ของเจ้าของ: หน้าตั้งค่าแสดง identity ของ OA หอ** — บล็อก "OA ของหอ" ในส่วน *LINE เจ้าของ* แสดงชื่อที่แสดงและ `basicId` (เช่น `Chumsaeng (DEV) · @490secnd`) พร้อมปุ่มคัดลอก ให้เจ้าของทำตามขั้นตอน "เพิ่มเพื่อน OA แล้วพิมพ์รหัส" ได้จริง · ค่ามาจาก `GET /v2/bot/info` ของ LINE เอง (`fetchBotInfo`) **ไม่ต้องมีใครกรอก จึงไม่มีทางพิมพ์ผิดและเปลี่ยนตามเมื่อตั้งชื่อบอทใหม่** · cache ลงตาราง `meta` key `line_bot_info` อายุ 6 ชั่วโมงเพื่อไม่ให้เปิดหน้าตั้งค่าทีไรต้องรอ LINE ทุกครั้ง — ดึงไม่ได้จะใช้ค่าเก่าต่อ แต่จะไม่ cache ความล้มเหลว (พอ LINE กลับมาต้องได้ค่าจริง) และถ้ายังไม่เคยมีค่าก็แสดงคำแนะนำโดยไม่มี id พร้อมบอกให้เปิด LINE Messaging API ก่อน (หน้าตั้งค่าไม่ล้ม)
- **บอกว่าใครเชื่อมอยู่ + เลิกเชื่อมได้** — `settings.ownerLineDisplayName` (ชื่อที่แสดงของบัญชีที่ผูกอยู่) มาจาก `line_pending` ก่อน แล้วตกลงไปที่ `fetchProfile` · แยกความหมาย `null` = ยังไม่ผูก กับ `""` = ผูกแล้วแต่อ่านชื่อไม่ได้ (หน้าจอแสดงต่างกัน) · `DELETE /api/settings/owner-link` ล้าง `owner_line_user_id` + รหัสทั้งสองคีย์ + `line_pending` ของบัญชีเดิมใน `DB.batch` เดียว — **รหัสเดิมต้องใช้ไม่ได้ทันที** ไม่งั้นคนถือรหัสเก่าจะผูกกลับเข้ามาได้เอง (อ่าน userId ก่อน batch เพราะคำสั่งลบต้องรู้ว่าจะลบ pending ของใคร ถ้าใส่ subquery ในชุดเดียวกันจะเห็นค่าใหม่ที่เพิ่งเขียน) · หลังเลิกเชื่อม หน้าตั้งค่าจะออกรหัสใหม่ให้เองตามตรรกะใน `loadSettings`
- **เปลี่ยน LINE OA: `GET /api/settings/line-channel` + `POST /api/settings/line-channel/webhook`** — สถานะช่องที่ใช้อยู่บอกว่า token ชี้ไป OA ตัวไหน (`fetchBotInfo`), secret ตั้งไว้หรือยัง, **webhook ที่ LINE ตั้งไว้จริงเทียบกับที่ควรเป็น** (`fetchWebhookEndpoint`) และ `webhookPointsHere` · ปุ่ม "ตั้ง webhook ให้ระบบนี้" เรียก `PUT /v2/bot/channel/webhook/endpoint` ให้ — **เขียนได้เฉพาะ endpoint ของ Worker ที่รับคำขอนั้น** (origin เดียวกัน) กันคำขอที่หลุดเข้ามาตั้ง webhook ไปชี้โดเมนอื่นซึ่งจะพาข้อความผู้เช่าไปผิดที่แบบเงียบ ๆ · ตรวจนี้จับเคสจริงที่เจอ: LINE ชี้ webhook ไป Worker อีกตัว (production) ขณะที่รหัสที่แสดงมาจากเครื่อง dev → พิมพ์รหัสแล้ว "ดูเหมือนไม่มีอะไรเกิดขึ้น" โดยไม่มีสัญญาณในหน้าจอ
- **เปลี่ยน OA ต้องทำ 3 อย่าง** (credential ไม่ถูกเก็บลงฐานข้อมูลโดยตั้งใจ — หน้าจอแสดงคำสั่งให้รัน): (1) `wrangler secret put LINE_CHANNEL_ACCESS_TOKEN` และ `LINE_CHANNEL_SECRET` (2) ตั้ง webhook ผ่านปุ่มในหน้า หรือ `PUT` endpoint เอง (3) แก้ `LIFF_ID` ใน `wrangler.jsonc` ถ้าเปลี่ยน LIFF app · **`tenants.line_user_id` / `owner_line_user_id` ไม่ต้องแก้ถ้า OA ใหม่อยู่ใต้ LINE Provider เดิม** เพราะ userId ผูกกับ provider ไม่ใช่ channel (LINE ระบุชัดว่า provider เดียวกันให้ userId เดียวกัน แม้คนละช่อง) — ถ้าย้าย provider ต้องให้ผู้เช่าพิมพ์เลขห้อง + เบอร์ 4 ตัวท้ายใหม่ และเชื่อมเจ้าของใหม่
- ข้อความ text ที่ตรงกับคีย์เวิร์ดของเมนูหลัก (`ส่งสลิป` `บิลของฉัน` `ติดต่อเจ้าของ` `ลงทะเบียน`) ถูกจัดการ **ก่อน** ทุกอย่างอื่น (ตัดช่องว่างหัวท้ายแล้วเทียบแบบตรงตัว): `ส่งสลิป` → คำแนะนำให้ส่งรูปสลิปในแชท, `บิลของฉัน` → บิลล่าสุดของห้องพร้อมเดือน/ยอด/สถานะ (ผู้ใช้ที่ยังไม่เชื่อมจะได้คำแนะนำให้ลงทะเบียนพร้อมลิงก์), `ติดต่อเจ้าของ` → ชื่อและช่องทางติดต่อของเจ้าของจาก `owner_name`/`owner_phone`/`owner_line_id` (แถว **LINE ส่วนตัวของเจ้าของ** มีปุ่มคัดลอกให้วางในช่องค้นหาของแอป LINE; ช่องไหนว่างก็ซ่อนแถวนั้น ถ้าว่างทั้งเบอร์และ LINE จะบอกว่ายังไม่ได้บันทึกช่องทางติดต่อและให้ฝากคำถามไว้ในแชท) — **`owner_line_id` ต้องเป็น LINE ส่วนตัวของเจ้าของเท่านั้น ห้ามใส่ id ของ OA หอ (`@490secnd`)**: ผู้เช่าที่อ่านการ์ดนี้กำลังคุยอยู่ในแชทของ OA นั้นอยู่แล้ว การส่ง id กลับไปจึงชี้ไปบัญชีที่เขาใช้งานอยู่ ไม่ใช่ช่องทางใหม่ ฝั่ง server และ client ปฏิเสธค่านี้พร้อมข้อความบอกเหตุผล, `ลงทะเบียน` → ลิงก์ลงทะเบียน (`https://liff.line.me/{LIFF_ID}` เมื่อตั้งค่า `LIFF_ID` ไม่งั้นใช้ `/register` ของ origin แอป) — ผู้ใช้ที่ยังไม่เชื่อมไม่ถูกเมิน ส่วนผู้เช่าที่เชื่อมแล้วพิมพ์คีย์เวิร์ดจะได้คำตอบแต่ข้อความอื่นของเขายังถูกเมินเหมือนเดิม
- ข้อความที่บอทส่งกลับ (ทั้ง `reply` และ `push`) เป็น Flex card จาก `src/worker/line/messages.ts`: หัวข้อพื้นสีตามความหมายโดยใช้ **token สถานะชุดเดียวกับ badge ของแอป** (สำเร็จ = paid `#dcfce7`/`#15803d`, ข้อมูล = unpaid `#dbeaff`/`#1e40af`, รอดำเนินการ = review `#fff7e6`/`#b45309`, ไม่สำเร็จ/ซ้ำ = danger-soft `#fef2f2`/`#b91c1c` — ทุกคู่ผ่าน WCAG AA), เนื้อเป็นแถว label/value คั่นเส้นบาง `#E5E5E5`, ปุ่ม primary ใช้ ink `#171717` เดียวกับ `.btn-primary` ของแอป (ไม่ใช่น้ำเงิน `#2563eb` ที่ DESIGN.md สงวนไว้เป็นสีเน้น), `altText` เป็นประโยคไทยสั้น ๆ และมี footer ปุ่มเฉพาะเมื่อมีลิงก์จริง เช่นปุ่มเปิดหน้าลงทะเบียน — ไม่มีรูป/emoji/เครื่องหมายอัศเจรีย์; ยกเว้นข้อความลงทะเบียนถึงเจ้าของ/ผู้เช่าใน `routes/register.ts` และสรุปหลังส่งบิลถึงเจ้าของใน `routes/bills.ts` ที่ยังเป็นข้อความ text
- event `message` ที่เป็นรูป (`message.type = "image"`) → ถือเป็นสลิปการโอนของห้องผู้ส่ง ไปที่หัวข้อ "สลิป และการปิดบิลอัตโนมัติ" ด้านบน (ผู้ส่งที่ยังไม่เชื่อม LINE จะได้ข้อความให้พิมพ์เลขห้องก่อน)
- `/api/line/pending` (GET) และ `/api/line/pending/:lineUserId/link` (POST) อยู่หลังการล็อกอิน ใช้โดยหน้าผู้เช่าในส่วนจัดการการเชื่อม LINE
- **หน้าข้อความ LINE (`#line`) มีตัวกรองตามผู้รับ** — segmented control เหนือรายการ (`ทั้งหมด 11` / `ถึงผู้เช่า 8` / `ถึงเจ้าของ 3`) ใช้ pattern เดียวกับหน้ารอตรวจและหน้าบิล (`role="group"` + `aria-pressed` + `bg-status-unpaid-bg` ของตัวที่เลือก) ยอดนับอยู่ในป้ายจึงรู้จำนวนของแต่ละฝั่งโดยไม่ต้องเปิดดู · ตัวกรองทำงานร่วมกับ `activeKey` โดยการ์ดที่เลือกอยู่ต้องอยู่ในชุดที่กรองไว้เสมอ (ถ้าหลุดออกจะตกกลับไปใบแรกของชุดใหม่) และลูกศรเลื่อนใช้รายการที่กรองแล้ว · เป็นเรื่องจำเป็นเพราะการ์ดของเจ้าของปนอยู่ในลิสต์เดียวกับของผู้เช่าตามลำดับที่ server ส่ง (ตำแหน่ง 3, 10, 11)
- **`GET /api/line/messages` (แคตตาล็อกสำหรับหน้า "ข้อความ LINE")** — คืน `{ok, source, lastSent, messages}` โดย `messages` เป็นการ์ดจริงที่ระบบส่งทุกแบบ สร้างจาก payload ของ **บิลจริง** (บิลล่าสุดของห้องแรกในรอบล่าสุด) ไม่ใช่ข้อความตัวอย่างที่แต่งขึ้น: `source` = `{period, roomNumber, tenantName}` บอกว่าใช้บิลใบไหนเป็นที่มา และ `lastSent` = `{sentAt, roomNumber, period}` คือการส่งบิลจริงครั้งล่าสุดจาก `bills.sent_at` (`null` เมื่อยังไม่เคยส่ง) — **สองค่านี้ตอบคนละคำถาม**: `source` คือ "เนื้อหาตัวอย่างมาจากไหน", `lastSent` คือ "ส่งจริงหรือยัง เมื่อไร" หน้าที่นี้จึงตอบได้ทั้ง "ใครได้รับ" และ "เมื่อไร" โดยไม่ต้องออกไปหน้าบิล · การ์ดที่ต้องพึ่งบิล (`bill`, `payment`, `owner_bill_paid`, `owner_slip`, `owner_send_summary`) จะหายไปเมื่อยังไม่มีบิล
- ข้อความบิลที่บอท push เป็น Flex message ที่แนบรูป QR พร้อมเพย์และปุ่มเปิดใบแจ้งหนี้ PDF ของบิลนั้น — ทั้งคู่คือสอง route สาธารณะ `/qr/:billId.png` และ `/invoices/:billId.pdf` ด้านบน จึงต้องเป็นสาธารณะจริง ไม่ต้องล็อกอิน
- ตรวจ signature แบบ synchronous ก่อนทุกอย่าง (เหมือนเดิม) แต่ **ตอบแล้วค่อยทำงาน**: signature ผิด/ไม่มา → `403` และไม่แตะฐานข้อมูล, body ที่ parse ไม่ได้ → `200 {ok: true}` เฉย ๆ, เมื่อ signature ผ่าน → `200 {ok: true}` ทันทีโดยยังไม่ประมวลผล event
- งานของ event ทั้งหมด (reply, push, เขียน DB, ดาวน์โหลดรูป, ตรวจสลิปกับ SlipOK ที่กินเวลาหลายวินาที) รัน **หลัง** ตอบกลับไปแล้ว ผ่าน execution context ของ request (`c.executionCtx.waitUntil`) จึงไม่ค้างจนเกินเวลาที่ LINE รอ — เดิมประมวลผล inline จน LINE ตัดไปก่อน (Cloudflare ขึ้น `Canceled` แล้ว invocation ถูกฆ่ากลางทาง งานที่ทำค้างไว้หายครึ่ง ๆ กลาง ๆ: สลิปถูกสร้างแถวแล้วแต่ `verify_result` เป็น NULL ตลอดกาล) และเพราะ redelivery ของ LINE ปิดอยู่โดยค่าเริ่มต้น การตอบ non-2xx จึงไม่ได้ทำให้งานถูกลองใหม่ มีแต่ทำให้ LINE มองว่า webhook พังทั้งชุด จึง**ตอบ `200` เสมอ**เมื่อ signature ผ่าน
- event ที่ประมวลผลล้มเหลว (เช่น เขียน DB ไม่ได้) ถูก log แบบมีโครงสร้างว่า `line webhook failed` พร้อม **ปล่อยสิทธิ์คืน**ใน `line_events` เพื่อให้กดส่งซ้ำด้วยมือ (หรือเปิด redelivery ในอนาคต) ทำงานได้จริง ไม่ถูกมองว่า "ทำไปแล้ว" — ความล้มเหลวชนิดนี้ไม่มีสลิปให้ผูกจึงไม่มีที่ให้แสดงนอกจาก log (ต่างจากสลิปที่ตรวจไม่ได้ ซึ่งเจ้าของหอเห็นเหตุผลในหน้ารอตรวจ)

- `assets/rich-menu/rich-menu.png` — รูปที่เรนเดอร์แล้ว ขนาด 2500 × 1686 พิกเซล

ปุ่มทั้งสี่และ action:

| ช่อง | ปุ่ม | action |
|------|------|--------|
| ซ้ายบน | ลงทะเบียนผู้เช่า | `uri` → `https://liff.line.me/{LIFF_ID}` |
| ขวาบน | ส่งสลิป | `message` → `ส่งสลิป` |

| ขวาล่าง | ติดต่อเจ้าของ | `message` → `ติดต่อเจ้าของ` |

`scripts/rich-menu.mjs` เป็น ESM ล้วน ไม่มี dependency ใช้ `LINE_CHANNEL_ACCESS_TOKEN` และ `LIFF_ID` จาก environment ก่อน ถ้าไม่มีจึงอ่านจาก `.dev.vars` ถ้าไม่มี token จะหยุดพร้อมข้อความบอก ถ้าไม่มี `LIFF_ID` จะไม่สร้างเมนูเพราะปุ่มลงทะเบียนจะกลายเป็นลิงก์ตาย สคริปต์พิมพ์แค่ id ไม่เคยพิมพ์ token (รันผ่าน `npm run` หรือ `node scripts/rich-menu.mjs` ก็ได้)

```bash
npm run rich-menu                              # สร้างเมนู + อัปโหลดรูป + ตั้งเป็นเมนูหลักของทุกคน
npm run rich-menu:list                         # ดูเมนูทั้งหมดของ OA
npm run rich-menu:delete -- richmenu-xxxxxxxx  # ลบเมนูตาม richMenuId
```

`npm run rich-menu` เรียก `POST /v2/bot/richmenu` แล้ว `POST /v2/bot/richmenu/{richMenuId}/content` ที่โฮสต์ `api-data.line.me` แล้วปิดท้ายด้วย `POST /v2/bot/user/all/richmenu/{richMenuId}` ถ้าขั้นไหนล้มเหลวจะพิมพ์ HTTP status และ body ที่ LINE ตอบกลับมาให้เห็นว่า LINE ไม่รับตรงไหน

ข้อความตอบกลับของปุ่มแบบ `message` (`ส่งสลิป` `บิลของฉัน` `ติดต่อเจ้าของ`) และคำสั่งพิมพ์เอง `ลงทะเบียน` อยู่ในฝั่ง webhook (`handleTextMessage` ใน `src/worker/routes/line.ts`) แยกจากสคริปต์นี้ ข้อความตอบกลับทั้งหมดเป็น Flex card ที่สร้างจาก `src/worker/line/messages.ts`

## ลงทะเบียนผู้เช่าด้วย LIFF

ผู้เช่าเปิดลิงก์ LIFF จากในแชท LINE กรอกชื่อ-นามสกุล เบอร์โทร และเลือกห้องที่ว่าง ระบบยืนยันตัวตนด้วย access token ของ LIFF ฝั่งเซิร์ฟเวอร์ แล้วสร้างผู้เช่า ผูก LINE แจ้งเจ้าของ และยืนยันกลับให้ผู้เช่า — เจ้าของไม่ต้องกรอกข้อมูลเอง

### หน้าลงทะเบียน (สาธารณะ)

- `GET /register` — หน้าฟอร์ม LIFF เป็น HTML เดี่ยว (ไม่ใช่ SPA และไม่ผูกกับเปลือกแอป) โหลด LIFF SDK แล้ว `liff.init({ liffId })` โดยอ่าน LIFF ID จาก env `LIFF_ID` แล้ว `liff.getAccessToken()`; ถ้า `LIFF_ID` ว่าง เปิดนอกแอป LINE หรือ init ไม่สำเร็จ จะแสดงข้อความภาษาไทยให้เปิดจากในแอป LINE เท่านั้น พร้อมขั้นตอนตั้งค่าที่เจ้าของต้องทำ — ไม่มีหน้าจอพังหรือเงียบ
- ฟอร์มมี ชื่อ-นามสกุล / เบอร์โทร / ห้อง (dropdown จาก `GET /api/register/rooms` โหลดใหม่ทุกครั้งที่เปิดหน้า) ปุ่มส่งที่มีสถานะกำลังทำงาน การตรวจค่าในหน้าแบบ inline และหน้าสำเร็จที่โชว์ชื่อ+ห้องพร้อมปุ่ม `liff.closeWindow()`; ข้อความ error จากเซิร์ฟเวอร์ (`409`/`401`) แสดงในหน้าและให้แก้ไขส่งใหม่ได้ — หน้าออกแบบตาม `DESIGN.md` ด้วยชุดสีของแอป (พื้นโทนกระดาษ เส้นขอบ 1px มุมโค้ง และปุ่มหลักสีเข้มทึบ) ใช้ฟอนต์ไทยชุดเดียวกับแอป (Inter + Noto Sans Thai) และไม่มี dependency/ขั้นตอน build
- หน้าอยู่ก่อน SPA fallback ด้วยการเพิ่ม `/register` ใน `assets.run_worker_first`

### Endpoints (สาธารณะ)

- `GET /api/register/rooms` — คืน `{ ok: true, rooms: [{ id, roomNumber }] }` เฉพาะห้องที่ว่าง เรียงตามเลขห้อง ไม่มีชื่อผู้เช่า ค่าเช่า หรือข้อมูลอื่นติดออกไป
- `POST /api/register` — body `{ name, phone, roomId, accessToken }`; ตรวจค่าก่อนแตะฐานข้อมูล (ชื่อ ≥ 2 ตัวอักษร, เบอร์โทรไทย 10 หลักเริ่มด้วย 0 โดยตัดช่องว่าง/ขีดออก, `roomId` และ `accessToken` ต้องไม่ว่าง) → `400` พร้อม `field`; แล้วเรียก `GET https://api.line.me/v2/profile` ด้วย `Authorization: Bearer {accessToken}` เพื่อยืนยันตัวตน **ฝั่งเซิร์ฟเวอร์เสมอ ไม่รับ userId จาก body** (ล้มเหลวทุกกรณี → `401` "ลิงก์ยืนยันตัวตนไม่ถูกต้อง กรุณาเปิดฟอร์มจาก LINE อีกครั้ง" และไม่สร้างอะไร) ใช้ `userId` ที่ได้เป็นตัวตน; LINE ที่ผูกกับผู้เช่าอยู่แล้ว → `409` (บอกเลขห้องในข้อความ); ไม่พบห้อง → `404`; ห้องที่มีผู้เช่าอยู่แล้ว → `409`
- เมื่อผ่านทุกข้อ: สร้างผู้เช่าด้วยกฎเดียวกับ `POST /api/tenants` (วันเข้า = วันนี้, ห้องเป็น `occupied`, ผ่าน partial unique index หนึ่งผู้เช่าปัจจุบันต่อห้อง) พร้อมลบแถว `line_pending` ของผู้ใช้นั้นใน `DB.batch` เดียว → แล้ว (หลัง commit, แบบ fail-soft) push `ผู้เช่าลงทะเบียนใหม่: {ชื่อ} ห้อง {เลขห้อง} เบอร์ {เบอร์}` ถึงเจ้าของ (เฉพาะเมื่อมี `settings.owner_line_user_id`; ล้มเหลวไม่ทำให้คำขอพัง) และ push ข้อความยืนยันสั้นๆ ถึงผู้เช่า → ตอบ `200 { ok: true, tenant: { name, roomNumber } }`; ความล้มเหลว log แบบมีโครงสร้าง
- อยู่ **นอกการล็อกอิน** เหมือน `/webhook/*` และ `/qr/*`/`/invoices/*` เพราะเปิดจากใน LINE ก่อนผู้ใช้ล็อกอินได้ (ต่างจาก `/slips/*` ที่ต้องล็อกอินแล้ว) — `/api/*` glob ครอบ `/api/register/*` อยู่แล้ว ส่วน `/register` ถูกใส่ใน `run_worker_first` ด้วย

`migrations/0010_auth_families.sql` และตรรกะที่ `src/worker/lib/auth.ts`, `src/worker/routes/auth.ts`,
`src/worker/routes/family.ts`

ข้อมูลทั้งหมด (ห้อง ผู้เช่า บิล ตั้งค่า) ผูกกับ "ครอบครัว" (family) ไม่ใช่ผู้ใช้คนเดียว —
สมาชิกในครอบครัวเห็นข้อมูลชุดเดียวกันผ่านหน้าครอบครัว มีสิทธิ์สองระดับคือ `owner` (จัดการสมาชิก
เชิญคนเพิ่ม ถอดคนออก) และ `member` (ใช้งานข้อมูลปกติ และดูรายชื่อคนในครอบครัวได้อย่างเดียว —
ไม่เห็นรายการคำเชิญของเจ้าของ) ครอบครัวต้องมีเจ้าของอย่างน้อยหนึ่งคนเสมอ — ลดตำแหน่งหรือถอดเจ้าของ
คนสุดท้ายออกไม่ได้ แม้กดพร้อมกันจากสองอุปกรณ์ (บังคับด้วยเงื่อนไขในคำสั่ง SQL เดียว ไม่ใช่ SELECT
ตรวจก่อนแล้วค่อยเขียน)

**หนึ่งครอบครัวรับได้สูงสุด 2 คน** (นับเจ้าของรวม) ตัวเลขอยู่ที่ `maxFamilyMembers` ใน
`src/worker/lib/auth.ts` และถูกบังคับตอน *เข้าครอบครัว* ด้วยเงื่อนไขนับในคำสั่ง INSERT เดียว
ทั้งทางรับคำเชิญและทาง Google จึงแข่งกันเข้าพร้อมกันแล้วเกินเพดานไม่ได้ ส่วนตอนออกคำเชิญมี
การเตือนตั้งแต่ต้นเพื่อไม่ให้ออกใบที่ไม่มีวันถูกใช้ — หนึ่งบัญชีอยู่ได้ครอบครัวเดียว บังคับที่
ฐานข้อมูลด้วย unique index `idx_family_members_single_family` บน `user_id`

**ตั้งเจ้าของหอคนแรก** — ไม่มีรหัสลับให้ต้องไปหาจากที่ไหนแล้ว: ตั้งอีเมลเจ้าของไว้ใน `vars`
ของ `wrangler.jsonc` (`OWNER_EMAIL` เป็นค่าธรรมเนียม ไม่ใช่ secret) แล้วเปิดหน้าเว็บครั้งแรก
กด "ตั้งเจ้าของหอครั้งแรก" ใส่อีเมลนั้นพร้อมชื่อหอ — `POST /api/auth/setup` รับได้เฉพาะอีเมลที่
ตรงกับ `OWNER_EMAIL` และเฉพาะตอนที่ครอบครัวเดิมยังไม่มีเจ้าของ ข้อมูลเดิมก่อน migration 0010
(ห้อง ผู้เช่า บิลทั้งหมด) จึงตกเป็นของบัญชีนั้น มุมแลกเปลี่ยนคือคนที่รู้หรือเดาอีเมลนี้ได้และ
ตั้งบัญชี *ก่อน* เจ้าของตัวจริงจะทำได้ — ตั้งบัญชีให้เสร็จทันทีหลัง deploy

การเพิ่มคนเข้าครอบครัวทำได้ทางเดียวคือคำเชิญจากเจ้าของ (`POST /api/family/invites` คืนลิงก์
ที่มี token ดูซ้ำไม่ได้ เพราะเก็บแค่ hash) และ **ไม่มีการสร้างครอบครัวใหม่จาก endpoint สาธารณะอีกแล้ว**

**เข้าสู่ระบบด้วย Google (ไม่บังคับ)** — ตั้ง `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`
(ชนิด Web application) แล้วเพิ่ม Authorized redirect URI ทั้ง
`http://localhost:5173/api/auth/google/callback` และ
`https://wangchan-dorm.nodhk2545.workers.dev/api/auth/google/callback` ถ้าไม่ตั้ง ปุ่ม Google
จะขึ้นว่าเซิร์ฟเวอร์ยังไม่ได้ตั้งค่า ส่วนอีเมลและรหัสผ่านยังใช้ได้ตามปกติ
`GET /api/auth/google/start` พาไปหน้าเลือกบัญชีของ Google พร้อม state ที่เก็บในคุกกี้ชั่วคราว
(`SameSite=Lax` จึงยังถูกส่งตอน Google เด้งกลับ) แล้ว `GET /api/auth/google/callback` แลก code
เป็น access token ฝั่งเซิร์ฟเวอร์ (client secret ไม่เคยออกไปฝั่งเบราว์เซอร์) แล้วถามโปรไฟล์จาก
`userinfo` endpoint — ยอมรับเฉพาะอีเมลที่ Google ยืนยันแล้ว (`email_verified`)

บัญชีที่ผูกกับอีเมลนั้นจะถูกล็อกอินให้ทันที ซึ่งเป็นทางกู้รหัสผ่านไปในตัว: **ลืมรหัสผ่านให้กด
"เข้าสู่ระบบด้วย Google" ด้วยอีเมลเดียวกัน** ไม่ต้องรออีเมลรีเซ็ต ถ้าอีเมลนั้นยังไม่มีบัญชีและยังไม่
ถูกเชิญ ระบบจะปฏิเสธ (ไม่เปิดสมัครอิสระ)

**อัตราจำกัดการล็อกอิน** — ผิดรหัสผ่าน 8 ครั้งภายใน 15 นาที (นับแยกทั้งต่ออีเมลและต่อ IP) ได้ 429
**CSRF** — คำขอที่เปลี่ยนข้อมูล (POST/PUT/PATCH/DELETE) ที่มี header `Origin` ไม่ตรงกับโดเมนตัวเอง
ถูกปฏิเสธด้วย 403 แม้จะมี cookie ที่ถูกต้องมาด้วยก็ตาม

ยังคงใช้ Cloudflare Access เป็นชั้นป้องกันเพิ่มได้ (defense in depth) แต่ไม่จำเป็นแล้ว เพราะแอป
บังคับล็อกอินเองทุก path ที่มีข้อมูลของผู้เช่า รวมถึง `/slips/:file` (รูปสลิป) ที่เดิมเคยเปิดสาธารณะ
ด้วยเหตุผลว่าคีย์รูปเดาไม่ได้ — เหตุผลนั้นไม่พอ เพราะลิงก์ที่รั่วออกไป (แชร์ผิด, log, proxy) ยังดูรูปได้
ตลอดกาลโดยไม่ต้องล็อกอิน จึงเปลี่ยนมาบังคับ session cookie และตรวจว่าเป็นครอบครัวเดียวกับสลิปนั้นก่อน
เสิร์ฟรูปทุกครั้ง (ดูหัวข้อ "สลิป และการปิดบิลอัตโนมัติ" ด้านบน) — ส่วน `/qr/*` และ `/invoices/*` ยังต้อง
สาธารณะด้วยเหตุผลเดิมคือลิงก์ถูกส่งออกไปในข้อความ LINE ของผู้เช่า

การจัดการ asset และ API:

- `assets.run_worker_first` เป็น array ของ glob `["/api/*", "/health", "/webhook/*", "/qr/*", "/slips/*", "/invoices/*", "/register"]` ทำให้ path เหล่านี้วิ่งเข้า Worker เสมอ ส่วน path อื่นถูกเสิร์ฟเป็น static asset และ fallback เป็น SPA (`not_found_handling: "single-page-application"`) — `/register` ต้องอยู่ในลิสต์นี้ ไม่งั้นจะได้ `index.html` ของ SPA แทนหน้าลงทะเบียน
- ถ้าเพิ่ม path API ใหม่ ต้องเพิ่ม glob ใน `assets.run_worker_first` ด้วย ไม่งั้นจะได้ index.html แทน JSON

**ticket 10 เพิ่ม**: สลิปเข้าคิวแล้ว push แจ้งเจ้าของถูกเนื้อหา (ห้อง ชื่อผู้เช่า ยอดในสลิป vs ยอดบิลที่เทียบ และกรณีไม่มีบิลค้างบอกว่าไม่มีบิลให้เทียบ), เจ้าของยังไม่เชื่อม LINE = ไม่มี push และไม่มีอะไรพัง, `GET /api/slips` คืนเฉพาะ `pending_review` โดยปริยายพร้อมฟิลด์ที่หน้า รอตรวจ ใช้ครบ (path รูป, reason, ยอดในสลิป, ห้อง/เดือน/ยอดของบิลที่เทียบ) และ `?billId=` / `?status=` กรองได้ตามสัญญา (`status` ผิดคำศัพท์ `400`), `settle` ปิดบิล (`transfer`, วันที่จากสลิป) + สลิป `matched` + push ยืนยันถึงผู้เช่า และสลิปหายจากคิว, `settle` ที่บิลจ่ายแล้ว/`trans_ref` ซ้ำ/สลิปที่ตัดสินแล้ว = `409` โดยไม่มีอะไรเปลี่ยน, `billId` ใน body ใช้ปิดบิลที่ยังไม่ผูกกับสลิปได้ (ไม่มีทั้งคู่ `400`, บิลไม่รู้จัก `404`), `reject` ทำสลิปเป็น `rejected` (บันทึก `decision`/`decidedAt`) บิลไม่เปลี่ยน ไม่ push, และ id ที่ไม่รู้จัก `404` ทั้งสองคำสั่ง; **เพิ่มภายหลัง**: คำตอบจริงของ SlipOK ที่มาเป็น **HTTP 400** พร้อม `data` สมบูรณ์ (รหัส 1014) ต้องไม่ทำให้ `transRef`/`amount` หาย — สลิปเข้าคิวพร้อมเลขอ้างอิงและยอดที่ผู้ให้บริการอ่านได้ และคิวส่งค่าทั้งสองต่อให้หน้า รอตรวจ, รหัส `1012` ที่มาเป็น HTTP 400 ต้องถูกปฏิเสธเป็น `duplicate_slip` โดยไม่แตะบิล, และเมื่อเรียกตรวจไม่สำเร็จ (503) หรือผู้ให้บริการบอกว่ายังตัดสินไม่ได้ (1009) สลิปต้องเข้า reason `verify_failed` พร้อม `code`/`detail` ที่หน้า รอตรวจ และข้อความแจ้งเจ้าของ นำไปแสดงได้ — รวมถึงรหัส `1007` (ไม่มี QR) ที่ต้องนับเป็น `not_verified` ไม่ใช่ `verify_failed` เพราะมี `code`/`message` ของจริงส่งกลับมา

## หมายเหตุเรื่อง UI

- **หัวตารางของหน้ารายการบิลค้างบนจอ** (`DataTable` รับ prop `stickyHeader` — เป็น opt-in หน้าอื่นไม่เปลี่ยน) ใช้คนละโหมดตามพื้นที่จริง เพราะ `position: sticky` ยึดกับ scrollport ที่ใกล้ที่สุด: ถ้ากรอบตารางแคบกว่าตัวตาราง (คอลัมน์รวม 1120px บนจอ ≤1440) กรอบจะเลื่อนในตัวเองและหัวค้างบนสุดของกรอบ (`overflow: auto` + `max-height: calc(100dvh - 13rem)`); ถ้าจอกว้างพอตั้งแต่ 1500px ขึ้นไป ใช้ `overflow-x: clip` (ไม่สร้าง scroll container) หัวจึงค้างกับหน้าเว็บที่ `top: 4rem` ตรงกับความสูงแถบหัวแอปพอดี — ต้องเท่ากับ 64px ไม่ใช่ 80px ไม่งั้นจะเกิดช่องที่แถวข้อมูลทะเล็ดขึ้นมาเหนือหัวตาราง
